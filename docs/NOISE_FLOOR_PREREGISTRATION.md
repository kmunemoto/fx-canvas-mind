## 1. 問い

**同じプロンプトをもう一度送ったとき、答えはどれだけの割合で変わるか。**

これは #65（現行ルールブック対候補ルールブックの対応のある比較・McNemar）の**前提条件**であって、
それ自体が目的ではない。この数を先に測っていなければ、#65 で観測された差は「ルールブックが効いた」と
「モデルが同じ入力に二度同じ答えを返さなかった」を**区別できない**。

このモデルには pin できるサンプリング設定が無い。`temperature`・`top_p`・`top_k` は受け付けられず
（送れば 400 が返る）、Messages API に `seed` は無い。つまり「既定値を記録する」ことはできず、
**ノイズはモデルの性質そのもの**である。記録するのは `output_config.effort` の値だけで、それが
思考の深さ＝分散の主な駆動輪である。

## 2. 主指標

**見出しは確信度の広がり。二値の不一致率はその帰結として下に置く。**

理由は母集団の検閲にある。床は厳密不等号（`confidence < 60` が WAIT、60 は公開される）で、
実測すると**どの行も 3 ポイント下がるまで 1 行も反転しない**：

| 下振れ d | 1 | 2 | **3** | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 反転する行 | 0 | 0 | **1** | 5 | 12 | 13 |

48 行の確信度の実測分布は 38 / 40 / 42×4 / 45×10 / 48×2 / 52×5 / 62 / 63×4 / 64×7 / 65 / 66×9 / 68×3。
床を超えているのは 25 行、下は 23 行。上向きは 52 の 5 行が 8 ポイント必要で、48 行中 23 行は
それ以下では動かない。53〜61 の帯に本番の行は**1 件も無い**（実測 0）。したがって二値指標は
「25 行の下向きジッタ」を 48 行の率として報告するものであり、検閲されていない量は**広がりだけ**である。

### 2.1 主指標（二値・#65 のセルと同一の関数）

**`published_proxy` = 確信度の床だけを通した、モデル自身の signal の二値化**
（`traded` = BUY か SELL、`waited` = WAIT）。行ごとに重み 1。

    disagree_i = [ C(N,2) − Σ_c C(n_ic,2) ] / C(N,2)
    p̂₀ = (1/n) · Σ_i disagree_i

N=2 では「2 回が違ったか」の指標関数に退化する。**ペアではなく行で平均する** — #65 の
McNemar の単位は行であり、再試行で反復が増えた行が重くなってはならない。

**これは「ユーザーに見えるもの」ではない。そう書かない。** 実測で、ゲートは 48 行中 26 行で
発火し（`low_confidence` 21、**`market_closed` 4、`poor_rr` 1**）、48 行中 3 行は
`entry_check.proposed_signal` と `analyses.signal` が食い違う。床以外の枝が発火した行は
**5/48 = 10.42%** で、§4 で導いた分岐点 9.06% を上回る。ただし**この 5 行のうち 2 行は確信度が
床の下にもあった**（`market_closed` かつ `confidence < 60`）ので、床だけの射影が実際の公開判断と
食い違うのは **3/48 = 6.25%** である。10.42% と 6.25% を両方書く。前者は「床以外の枝が動いた頻度」、
後者は「この射影が間違える頻度」で、別の量である。

それでも床だけを模すのは、ゲート全体を再現すると ATR・価格・3 つの閾値の揺れがモデルの揺れと
混ざって後から分離できないからであり、さらに `isPossiblyClosed(Date.now())` は**再生時の時計**を
読むので、週末に走らせれば両アームとも 100% WAIT になって完璧で無意味な 0% が出る。
`isPossiblyClosed` が閉と答える連続区間は金 21:00Z〜日 22:00Z の **49 時間**である（述語から数え直した。
`market-hours.ts` の `CLOSED_WINDOW_MS = 47` 時間は狭いほうの `isMarketClosed` の窓であって、
ゲートが読む述語のものではない）。**#65 は同一の射影を使うこと。** 使わないならこの床は #65 を gate しない。

- **生の signal の不一致率**: 併記するが主指標にしない。床通過後の指標の上位集合ではない

  ただし本番 48 行では `proposed_signal` は confidence の完全な関数（実測: トレード提案の最小確信度 62、
  WAIT 提案の最大確信度 52、例外 0 行）で、境界は空の 53〜61 帯にあるので、生の指標も同じ検閲を受ける。
- **両方がトレードした行に限った方向の不一致率**: 二重に失格。48 行のトレード提案 25 件は全部 SELL で、
  `entry_check.proposed_signal` を持つ `analyses` 58 行の生涯でも **SELL 35 / WAIT 23 / BUY 0** である

**BUY が 1 度でも返ったら二値化を再登録する。** 今日は二値と 3 値が数値として一致するが、
BUY↔SELL の反転は最大の不一致であり二値はそれを 0 と数える。3 値の集計も同時に記録する。

## 4. 「ノイズが大きすぎて比較できない」とする閾値

#65 は Δ=0.20、α=0.05 両側、検出力 80%。ノイズは b と c に対称に乗るので McNemar を偏らせない —
**薄める**。必要な対応ペア数は次で置く。

    ψ = 1/2 + (Δ/2)/(Δ + p₀)
    K = z_{α/2}/2 + z_β·√(ψ(1−ψ))
    n = 4K²(Δ + p₀)/Δ²

z_{α/2} = 1.959964、z_β = 0.841621。K は p₀=0 での 0.980 から、p₀→∞ での 1.401
（= 1.959964/2 + 0.841621·0.5）までしか動かないので、n は実質 p₀ に比例する。
Δ=0.20 として、**この文書のために計算し直した**値:

| p₀ | ψ | K | n（生） | 必要 n | 現在の 48 行 |
|---|---|---|---|---|---|
| 0（正確計算。下記） | — | — | — | **39** | 足りている |
| 0.05 | 0.900000 | 1.232468 | 37.97 | 38 | 足りている |
| 0.10 | 0.833333 | 1.293636 | 50.20 | 51 | +3 |
| 0.20 | 0.750000 | 1.344415 | 72.30 | 73 | +25 |
| 0.30 | 0.700000 | 1.365661 | 93.25 | 94 | +46 |
| 0.50 | 0.642857 | 1.383251 | 133.94 | 134 | +86 |

**p₀ = 0 の行は上の式では出せない。** ψ が 1 になって √(ψ(1−ψ)) が消え、n が 20 まで落ちるが、
p₀=0 では不一致ペアが片側に全部乗るので検定は符号検定になり、正規近似が効かない。正確に置き直す:
両側の正確二項検定が α=0.05 で棄却できるのは不一致ペアが **m ≥ 6** のとき（2·(1/2)⁶ = 0.03125 ≤ 0.05、
m=5 は 0.0625 で届かない）。不一致確率 Δ=0.20 として P(Bin(n, 0.2) ≥ 6) ≥ 0.80 を満たす最小の n は
**39**（検出力 0.8200。n=38 は 0.7996）。

**分岐点は 8.8% ではなく 9.06% である。** 必要 n がちょうど 48 に達する p₀ を上式から解くと
**p₀ = 0.09058**。設計の草案はここを 8.8% と書いていたが、8.8% は n が 47.39（切り上げて 48）に
なる点であって、48 行が足りなくなる点ではない。同じ解き方で、**中核 40 行しか使わないなら分岐点は
p₀ = 0.05783** である。以下の条件はこの 2 つの数の上に立っている。

- **主条件: p̂₀ の Wilson 95% 上限が 9% を超えたら「今ある行では #65 は判定できない」と書く。**
  点推定ではなく上限で判定する。9% は上で導いた 9.06% のすぐ下に置いた丸い数で、保守側である。
  帰結を先に書いておく: **48 行で上限が 9% を切るのは 0/48 のときだけ**（上限 7.41%）。
  1/48 で 10.90%。**満点以外は主条件を満たさない。**
  さらに、preview 4 行と v48 4 行は**互いに素**（実測 0 行の重なり）で、層別を要求するなら中核は
  40 行になり、0/40 の Wilson 上限は **8.76%**。これは中核 40 行の分岐点 5.78% を**超えている**。
  つまり**層別を主に据えるなら、この測定が返しうるどの結果（0/40 の満点を含む）も #65 を許可しない。**
  草案は 8.76% を「分岐点の真上」と書いていたが、比べる先が違っていた。**n=48 と n=40 を必ず並べて出す。**
- **絶望条件: 点推定が 30% 以上なら #65 は行数を増やしても救えない。** 134 行は観測ペース
  （直近 24 時間で 23 行）で数日だから母数の問題ではない。「現行ルールブックの答え」という対象が
  定義できておらず、片アーム 1 抽出は道具として間違っている。**k 回の多数決をアームにする**
  設計変更が必要で、呼び出し予算は k 倍になる。
- **器具条件: §3-3 の失敗率が 5% 以上なら結論を書かない。** モデルより先にハーネスが壊れている。
- **但し書き条件: 生の不一致率が主指標の 3 倍以上なら、主指標を単独で引用しない。**
  床がたまたま隠しているのであって、モデルが安定しているのではない。
- **p₀ が 5% から 30% にかけて、ノイズ 1 ポイントにつき対応ペアが約 2.24 行必要になる**
  （(94−38)/25 = 2.24）。
- **Δ=0.20 は仮定であり、p̂₀ と同じ検閲を受ける。** 候補ルールブックが 23 行を床の向こうへ動かすには、
  ノイズと同じく 8 ポイント動かす必要がある。上の表は Δ を固定して p₀ だけ動かしており、
  この 2 つはこの母集団では独立ではない。**表を出すときは必ずこの一文を添える。**

## 6. 何を送るか

**主アーム `search_free`: 48 行すべて、`tools` を外し、それ以外は本番がその行に送った値のまま、N=2。**
`system` と `user` は保存された通り**バイト単位で同一**。`max_tokens: 8000`。
検索由来の 45 行は `output_config = {effort:"low"}`（スキーマはプロンプト本文にそのまま残る、
その行の世代のまま）。technical の 3 行は
`output_config = {format:{type:"json_schema", schema: RESPONSE_SCHEMA}, effort:"medium"}` —
本番と同じ形。`cache_control` は付けない（本番は system も user も**素の文字列**で送っており、
ブロック配列にすることは形を変えることである。加えてキャッシュ可能な最小前置きはモデル依存で
512〜4096 トークンあり、この長さの system が届く保証が無い）。

**なぜバイトを触らないか。** もう一つの案は、行を `technical_fallback` のプロンプトに書き換える
（3 行目を差し替え、末尾のスキーマ節を切る）ものだった。**採らない。** それは一度に 4 つを変え、
うち 3 つは選択の余地があり（注記、スキーマが本文から `output_config.format` へ移る、effort が
low→medium）、後の 2 つはいずれも**分散を下げる**方向に働く。制約付きデコードは §3-3 の (iv) を
機構的に消し去る — 設計自身が「最も起きやすい」と名指した失敗源である。**下振れした床は、
#65 が本物のルールブック劣化をノイズとして見逃す方向の誤り**であり、最も避けたい向きである。
`tools` を外すだけなら変わるのは 1 つで、45 行が実際に通った散文パースの経路も (iv) も残る。

**代償は明記する。** 45 行のプロンプトは「まず検索せよ」と言っており、再生時のモデルは検索できない。
これは**アームの外部妥当性**の問題であって内部妥当性の問題ではない（比較は再生対再生であり、
保存された答えとは比べない）が、書かずに済ませない。

**副アーム `fallback_surgery`（比較用、見出しにしない）**: 検索由来 45 行の一部を上記の手術で送る。
主アームとの差が**手術の代償の直接測定**である。現在それはゼロと仮定されており、証拠は無い。

**副アーム `search_on`（上限、床ではない）**: `tools` を付けたまま。これはモデルのノイズ**＋** web の
ドリフトであり、応答からは分離できない。「replay stability」と呼び、床とは呼ばない。

**ユーザーに見えるものには一切触れない。** `analyses` / `lessons` / `rulebook` に書かない。
`analyze` エッジ関数を呼ばない（呼べば quota を消費し行を作る）。`analysis_prompts` は読むだけ。
**quota は 1 回も消費されず、返却も発生しない。**

**走らせる前に数える**。ただし `count_tokens` は**入力しか数えない**。出力は適応思考が出力レートで

## 7. 停止規則

**凍結した母集団の全行を N=2 で 1 パス。途中で結果を見ない。** 中間を見てから行を足したり落としたりしない。
transport 失敗は最大 3 回まで指数バックオフ、それでも失敗したら**その行を両反復ごと除外**し、
除外件数を報告する。**片方だけの行を作らない。**
`credit balance is too low` / 401 / 403 / 429 は**再試行せず run ごと中止**する。
`noise_runs.completed_cells + failed_cells < expected_cells` の間、レポートは率を出すことを拒否する。

**パイロットの扱い: パイロットのセルは p̂₀ に一切合算しない。** 目的は器具の検証であって
推定ではない。合算すれば「先に覗いてから母集団を決めた」ことになる。

## 8. 区間

**Wilson スコア 95% 両側。Clopper–Pearson を並べる。Wald は使わない。**
Wald は 0/48 で [0.0%, 0.0%] を返す — 何も観測しなかったことを「無いことを測った」と書くのが Wald で、
この repo の「読めなかったことはゼロではない」に真正面から違反する。

Wilson を選ぶ理由: 境界で退化しない（**47/48 行が床から 3 ポイント以上離れている**ので 0/48 は
十分ありうる。床に 2 ポイントまで寄っているのは確信度 62 の 1 行だけ）。
行は交換可能でなく各行が自分の p_i を持つ Poisson 二項だが、その分散
`Σp_i(1−p_i) = n·p̄ − Σp_i² ≤ n·p̄(1−p̄)`（Jensen）は二項分散**以下**なので、Wilson は保守側に外れる。
境界では正確区間との差が 0.02 ポイントに収まる（0/48 で Wilson 上限 7.410%、Clopper–Pearson 7.397%）。

以下はこの文書のために z=1.959964 で計算し直した表である。n=48 の 5 行と 0/40 は設計の草案と一致した。
**1/40 と 2/40 は草案（12.94% / 16.56%）と食い違い、計算し直した 12.88% / 16.50% を採った。**
連続性補正版でも草案の値にはならない。補正済みの上限は 0/40 で 10.91%、1/40 で 14.73%、2/40 で 18.21% で、
素の Wilson より一律に広い — 連続性補正は区間を**広げる向きにしか効かない**ので、素の
8.76% / 12.88% / 16.50% を下回る補正済み上限はそもそも存在しない。草案の 2 つは素の値をわずかに
上回るだけで補正版には遠く及ばず、補正の違いでは説明できない。同じ素の Wilson で 0/40 = 8.76% が
両方から出ることが、採否の根拠である。
**素の値より狭い「補正済み」上限を見たら、それは補正ではなく計算違いである。** 上限を小さく見せる
誤りは床を低く見せる誤りであり、#65 が本物の劣化をノイズと見誤る向きなので、ここに書き留めておく。

| k / 48 | p̂ | Wilson 95% | | k / 40 | Wilson 95% 上限 |
|---|---|---|---|---|---|
| 0 | 0.00% | [0.00%, **7.41%**] | | 0 | **8.76%** |
| 1 | 2.08% | [0.37%, 10.90%] | | 1 | 12.88% |
| 2 | 4.17% | [1.15%, 13.98%] | | 2 | 16.50% |
| 3 | 6.25% | [2.15%, 16.84%] | | | |
| 5 | 10.42% | [4.53%, 22.17%] | | | |

N=3 で走らせた場合 `disagree_i` は二値でなくなり Wilson は使えない。そのときは**行を単位とした**
ブートストラップ（10,000 回、行を再標本化する。反復ではない）の分位区間を副次として出し、
見出しは N=2 のままにする。

## 9. 前提が崩れる条件

- **主条件が満たされない** → #65 は今の行数では走らせない。§4 の n まで母集団が育つのを待つ。
  ただし新しい行は**新しい相場のスナップショット**であり、n を増やすことは検出力を買って均質性を売ることである。
- **絶望条件** → 多数決アームに設計し直す。
- **層別を主に据える判断をした** → §4 のとおり、0/40 でも中核 40 行の分岐点 5.78% を超える。
  そのときは「この測定では #65 を許可できない」が結論であり、結果の数字で読み替えない。
- **主アームと `search_on` の差が主アームの区間幅より大きい** → 「ノイズの床」は 1 つの数ではない。
  #65 は検索の設定を設計の一部として固定しなければならない。
- **主アームと `fallback_surgery` の差が主アームの区間幅より大きい** → 手術は無害ではない。
  #65 がプロンプトを触るなら、その代償を別に測る必要がある。
- **53〜61 の帯に反復が落ちる** → 本番の空白は 48 回の抽出の偶然だった。床通過後の指標が
  小さくても、それはこの母集団の確信度分布の性質であり、アナリストが安定していることの証拠ではない。
  この場合は広がりのほうを前に出す。
- **`response.model` が行の `model` と違うセルが出た** → サーバ側のモデル変更をアナリストのノイズとして
  数えている。そのセルは pool しない。

**逆に、p̂₀ が小さいことは「アナリストが正しい」ことを意味しない。** ここで測っているのは同じ問いに
対する 2 つの答えの一致率であって、その答えが当たっているかではない。

## 10. このデザインの既知の限界

- **`analysis_prompts` はリクエストの一部しか持っていない。** `max_tokens`、`output_config`、`tools`
  はどこにも保存されていない。再生は**今日のコードの形**で行われる。床としては問題ない（2 回とも
  同じ形だから）が、この床は各行が生まれたときの形の床ではない。
  とくに `effort` は、本番が `output_config` か `effort` を含むエラーを受け取ると**その場で外して
  再送する**分岐を持っており（`analyze/index.ts` の `effortEnabled`）、外れた回はモデルの既定値で
  答えている。それが起きたかどうかを残す列は無いので、「本番がその行に送った effort」は原理的に
  確認できない。§6 の「本番がその行に送った値のまま」は、正確には**今日のコードがその行のクラスに
  選ぶ値**である。両反復が同一なので床としては有効で、外部妥当性の側の但し書きである。
- **3 行の technical 行には今日の `RESPONSE_SCHEMA` が送られる。** その 3 行は v48 より前の世代で、
  `rules_applied` を見たことがない（実測: 本文にスキーマ節を持たず、末尾は定型文でちょうど終わる 3/3）。
  両反復が同一なので床としては有効だが、`schema_era` をセルに記録し、
  後から誰かが再生の答えを保存された答えと「同じフィールド集合」として比べないようにする。
  検索由来 45 行のスキーマ節は、マーカー `\n\n最終回答は<json>タグ内に` から末尾までで
  **2617 文字（41 行、md5 `5d3d5538fb27e74b37af2babeb2e2af4`）**または
  **2811 文字（4 行、md5 `5cfa2b6d1d26cf322bc5b3142929a7bc`）**。45/45 でマーカーは 1 回だけ現れ、
  末尾定型文の直後に接している（実測）。**世代を今日のスキーマ文字列との一致で判定してはならない。**
  そう書いた実装は 41 行を取りこぼす。
- **`sent_at` は API に送った時刻ではない**。`pricedAtIso`、価格の時刻である（実測で 48/48 が
  `analyses.priced_at` と一致）。`created_at − sent_at` の合計 **2709.658 秒**は fetch から write までの

  答えが割れるか」だけである。
- **保存された記録は検索が何をしたかを一切持っていない。** `analyses.context` の 12 キー（実測）に、
