### 1.1 【修正済み】metadata のキーが送信側と受信側で違う

決済は成立するのに、**プランが永久に上がらない**。

```
create-checkout/index.ts:89   metadata: { supabase_user_id: user.id, plan }
stripe-webhook（本番のみ）    const userId = session.metadata?.user_id;
```

`user_id` は常に `undefined` なので `if (userId && session.subscription)` の中身が丸ごと飛ぶ。
`profiles.plan` も `stripe_subscription_id` も書かれない。

**症状**: 利用者は課金されるが、アプリはずっと `free` のまま。「払ったのに使えない」。

**直した内容**: キーは `supabase_user_id` に統一。**送信側が前から送っていた方**を残したので、
修正前に作られた Stripe 上の顧客・セッションがそのまま使える（`user_id` に寄せると
それらが全部読めなくなる）。両方の関数で `USER_ID_METADATA_KEY` という定数に名前を付け、
2 つの文字列が一致することをテストで固定した。

受信側は `supabase_user_id` を先に読み、無ければ `user_id` も受け付ける。
これは対称性のためではなく、**ダッシュボードで手作りした支払いリンク**や古いデプロイが
作ったセッションを拾うため。送信側は定数しか使わないので、この寛容さは一方向で、
2 つの流儀が復活することはない。

### 1.3 【修正済み】未知の価格IDで、課金中の利用者を `free` に落とす

```
const plan = PRICE_TO_PLAN[priceId] || "free";
await supabase.from("profiles").update({ plan }).eq("stripe_customer_id", ...);
```

`customer.subscription.updated` は、金額変更・支払い方法変更・期間更新など**ふつうに何度も飛ぶ**。
`STRIPE_PRICE_*` が未設定、あるいは Stripe 上の価格IDと 1 文字でも違えば、そのたびに `free` に落ちる。

直し方: 未知の価格IDは**現状維持＋エラー記録**にする。プランを下げるのは
`customer.subscription.deleted` だけの仕事。

**直した内容**: 未知の価格IDでは `profiles` を**一切書かない**。`"free"` を書く箇所は
`customer.subscription.deleted` の 1 箇所だけになり、テストがそれを固定している。

**返すステータスは 2 つに分けた。**「未知」には性質の違う 2 つが混ざっていて、
最初はどちらも 500 にしていたが、それは**直した先の不具合より悪い**。

| 状況 | 返す | 理由 |
|---|---|---|
| `STRIPE_PRICE_*` が未設定（`missing` が空でない） | **500** | 再送の 3 日以内にシークレットを入れれば通る。再送を頼む意味がある |
| 対応表は揃っていて、単にうちの価格IDではない | **200**＋`console.error` | アーカイブ済みの価格、別商品、追加品目など。**何度再送しても通らない** |

後者を 500 にすると、その利用者の `customer.subscription.updated` が
**更新のたびに 3 日間失敗し続ける**。Stripe は失敗が続くエンドポイントに通知を出し、
最終的に**無効化する**。無効化されれば付与も剥奪も全員分止まるので、
`|| "free"` より影響範囲が広い。どちらの場合も**行は書き換えない**という肝心の部分は同じで、
違うのは「Stripe に何を頼むか」だけ。

なお後者に落ちたときの最終状態は「課金は取れた／プランは付与されない／記録は
Edge Function のログだけ」になる。**§3 の確認でここを監視対象に入れること。**

### 1.4 【修正済み】`STRIPE_PRICE_*` が未設定だと、対応表が壊れる

```
const PRICE_TO_PLAN = {
  [Deno.env.get("STRIPE_PRICE_LIGHT") || ""]: "light",
  [Deno.env.get("STRIPE_PRICE_STANDARD") || ""]: "standard",
  [Deno.env.get("STRIPE_PRICE_PRO") || ""]: "pro",
};
```

3 つとも未設定なら、キー `""` の 1 件だけを持つオブジェクトになる（最後の `pro` が勝つ）。
**一部だけ未設定の方が厄介**で、2 つは正しく引けて 3 つ目だけが `""` を共有するため、
壊れていることが見た目では分からない。

**直した内容**: 対応表は**設定済みの変数からだけ**組み立てる（未設定はキーにしない）。
`Map` を使うので、`constructor` のような名前の価格IDがプロトタイプ側に当たることもない。
未設定の変数は**名前だけ**を控えて、失敗時のログとレスポンスに出す（**値は絶対に出さない**）。

**当初案（起動時に落とす）は採らなかった。** モジュール読み込みで throw すると、
設定漏れのデプロイは**本文も理由も無い 500** を全配信に返すことになり、
ダッシュボードには「失敗」とだけ出て手掛かりが残らない。リクエストごとに読む方式なら
「どのシークレットが無いか」を名指しでき、シークレットを入れた後は
コールドスタートを待たずに次のリクエストから効く。

**この判断を、3 行上の 4 つの環境変数には適用し忘れていた。** → §1.10。

### 1.5 【修正済み】DB 更新の失敗を握り潰して Stripe に 200 を返す

```
if (error) console.error("DB update error:", error);
return new Response(JSON.stringify({ received: true }), ...);
```

Stripe は「届いた」と判断して再送しない。**課金は通ったがプランは上がらず、記録も残らない。**
DB 更新に失敗したら 5xx を返し、Stripe の再送に任せる。

**直した内容**: 書き込みの結果を必ず見るようにして、失敗なら 500 を返す。
**署名の検証失敗は 400 のまま**で、ここは意図的に区別している。署名が合わない本文は
5 回目でも合わない（Stripe 以外から来ているか、シークレットが別エンドポイントのもの）ので、
再送を頼むと 3 日分の再送枠を無駄にしたうえ、**本当に再送してほしい失敗が
同じ失敗件数に埋もれる**。ファイル内で 400 を返すのはこの 1 箇所だけ、とテストが固定している。

あわせて、**0 行しか一致しなかった更新も失敗として扱う**。Postgres は「1 行も一致しない
UPDATE」を成功として返すので、`stripe_customer_id` がまだ紐付いていない利用者への書き込みが、
プランを上げた書き込みと見分けが付かなかった。`.select("id")` で戻り行を数えて判定する。
ただし**解約（`deleted`）で 0 行のときだけは 200 で受ける** — 誰も有料プランを持ったままには
ならないし、よくある原因（利用者が退会済みで行が無い）は再送では直らないため。

### 1.7 【要確認・未修正】API バージョンが webhook 側とコード側で違う

- Webhook エンドポイントの登録: **2026-03-25.dahlia**

受信するイベントの本文はエンドポイント側のバージョンで組み立てられ、こちらから叩く API は
SDK 側のバージョンで返る。**この 2 つがずれていると、フィールドの位置が違う可能性がある。**

とくに `cancel-subscription/index.ts:76` の `updated.current_period_end` は、新しい API
バージョンで場所が変わっている可能性がある（Stripe のドキュメントはこの実行環境から参照できない
ため、**未確認**）。どちらかに揃えるのが正しく、揃える前に必ず Stripe のダッシュボードで
実際のイベント本文を 1 件見て確かめること。**推測で直さない。**

**今回は触っていない。** 3 つの関数の `apiVersion` は `"2023-10-16"` のまま。
`cancel-subscription` の `updated.current_period_end` もそのままで、コード側にも
**UNVERIFIED** としてコメントを残した。ここで防御的に `?? item.current_period_end` などと
書くのは、**誰も見たことがない形に対する当てずっぽう**で、修正に見えるだけで検証もできない。
なお、この項目が影響するのは**利用者に見せる解約日の表示だけ**で、解約処理そのものは通る。

うっかりバージョンが上がることを防ぐため、`src/test/payments.test.ts` が
3 つの関数の `apiVersion` が `"2023-10-16"` であることを固定している。
**このテストは現状を追認しているだけで、この組み合わせが正しいという意味ではない。**
バージョンを動かすときは、ダッシュボードで実配信を 1 件開いた状態で、テストごと更新すること。

### 1.8 【確認済み・対応不要】webhook の冪等性

Stripe は再送する（1.5 で 5xx を返すようにしたので、**こちらから意図的に再送させる**）。
同じイベントが 2 回届いたときに問題が起きないかを確認した。**起きない。**

書き込みはすべて `plan := light` / `stripe_subscription_id := sub_...`（または `null`）という
**絶対代入**で、加算でも追記でもない。同じイベントを何度当てても行の状態は同じになる。
これが 5xx で再送させても安全な理由でもある。

ただし、これは**見た目より狭い主張**なので、そこを取り違えないこと。安全なのは
**同じイベントの再送**であって、危ないのは**古いイベントが新しい状態の上に届くこと**。
後者は 1.8 の理屈では守れない。→ **§1.9 で別に対処した。**

**イベントIDの台帳（重複排除テーブル）は作らなかった。** テーブルが 1 つ増える割に、
本当に危ないケース＝**順序の入れ替わり**には何の役にも立たない。関係する 2 件は
どちらも「初めて見るイベント」なので台帳を素通りする。台帳は「対処済みに見える」だけになる。

代わりに、**全配信について 1 行のログ**を出すようにした（`event_id` と処理結果）。
元のコードはイベントの**種類**しかログに出しておらず、それはダッシュボードで既に見える
情報なので、「この配信が失敗した」から「関数が何をしたか」へ辿る手段が無かった。

```
{"event_id":"evt_...","type":"checkout.session.completed","outcome":"plan_granted","plan":"light"}
```

`outcome` はレスポンス本文にも入れてあるので、Stripe のダッシュボードの
「イベントの配信」画面からも理由が読める。

### 1.9 【修正済み】3 日後に届いた再送が、解約済みのプランを復活させる

**これは 1.5 の修正が新しく作った危険で、修正前には存在しなかった。**

1.5 の前は、失敗しても 200 を返していた。だから**再送そのものが起きなかった**。
5xx を返すようにした結果、配信は最大 3 日間再送される — そして
`customer.subscription.updated` の分岐は、届いたイベント本文の**スナップショット**を
そのまま信じて書き込んでいた。

```
1. 更新時に updated が届く → 書き込み失敗（または価格シークレット未設定）→ 500 → 再送開始
2. 利用者が解約 → deleted が届いて成功 → plan = free、stripe_subscription_id = null
3. 1 の再送が届く → stripe_customer_id で一致 → plan = light を書き戻す
```

利用者は**サブスクリプションが無いのに有料プランを持ったまま**になり、それを剥がせる
イベント（`deleted`）はもう消費済みなので、二度と剥がれない。ログには `plan_updated`、
つまり**成功として**残る。

**直した内容**: `customer.subscription.updated` と `checkout.session.completed` の両方で、
イベント本文を信じずに `stripe.subscriptions.retrieve()` で**現在の状態を読み直す**。
`canceled` / `incomplete_expired` のサブスクリプションには**絶対にプランを付与しない**。
3 日遅れの再送は `canceled` を読んで何もせずに終わる。

`past_due` / `unpaid` / `trialing` は**この集合に入れていない**。督促中の利用者から
途中でプランを取り上げるのは間違いで、それは Stripe 側の仕事。

読み直しには**もう 1 つ効果がある**。イベント本文はエンドポイント側の新しい API バージョンで
組み立てられる（§1.7）ので、そこから `items.data[0].price.id` を読むのは**誰も検証していない
形に対する読み取り**になる。`retrieve()` の戻りは SDK 側の固定バージョンで返るので、
**API バージョンを推測で動かさずに**ずれへの露出を減らせる。

**採らなかった案**: 台帳（§1.8 のとおり効かない）。もう 1 つ、
`profiles.stripe_subscription_id` とイベントのサブスクリプションIDの一致を要求する案は、
§1.15 の並び替えまで塞げるが、**このアプリが記録していないサブスクリプション**
（ダッシュボードで手作りしたものなど）の更新を黙って無視することになる。
これは不具合の修正ではなく方針の選択なので、オーナーの判断待ちにした。

### 1.10 【修正済み】シークレット未設定が「署名が不正」（400）と誤診される

`stripe-webhook` のモジュール先頭は、こうなっていた。

```
const stripe = new Stripe(Deno.env.get("STRIPE_SECRET_KEY")!, ...);
const WEBHOOK_SECRET = Deno.env.get("STRIPE_WEBHOOK_SECRET")!;
const supabase = createClient(Deno.env.get("SUPABASE_URL")!, Deno.env.get("SUPABASE_SERVICE_ROLE_KEY")!);
```

**`!` は TypeScript の型注釈で、実行時には何もしない。** `Deno.env.get` は `undefined` を返し、
その `undefined` がそのまま先へ渡る。ここから 2 つの別々の失敗が出る。

* `createClient(undefined, ...)` は**モジュール読み込みの時点で throw する**
  （`supabaseUrl is required.`）。読み込みで落ちる関数は、全配信に
  **本文も理由も無い 500** を返す — 1.4 で「これは避ける」と書いたその状態。
* **`STRIPE_WEBHOOK_SECRET` 未設定はもっと悪い。** `constructEventAsync(body, sig, undefined)` は
  throw し、その catch は `signature_verification_failed` として **400** を返す。
  つまり「シークレットをまだ入れていない」だけの運用者に、
  **「このリクエストは Stripe から来ていません」**と答える。しかも 400 なので**再送もされない**。
  シークレットを入れるのは**最も直しやすい**種類の失敗で、再送側に置くべきもの。

**直した内容**: 署名検証より**前に**、必須の 4 つ（`STRIPE_SECRET_KEY` /
`STRIPE_WEBHOOK_SECRET` / `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`）が入っているかを
リクエストごとに確認し、欠けていれば **`missing_required_env` として 500**（**名前だけ**を出す。
値は出さない）。クライアントの生成もハンドラの中に移したので、モジュール読み込みでは何も落ちない。
**400 を返す箇所はファイル内で 1 つだけ**という 1.5 の性質はそのまま。

### 1.11 【修正済み】metadata の `user_id` を検証せずに DB に投げる

1.1 の寛容さ（古い `user_id` も受け付ける）には、書いていなかった前提があった。
`user_id` は**ありふれた名前**で、この寛容さの理由そのものが
「create-checkout 以外が作ったセッションを拾うため」なのだから、そこに入っているのは
**Supabase の profile id とは限らない** — CRM のID、連番、メールアドレスかもしれない。

`.eq("id", "<uuid でない値>")` は静かに 0 件になるのではなく、**PostgREST が型エラーで弾く**
（22P02）。エラーになるので `db_update_failed` → 500 → **絶対に成功しない入力に対して
3 日間の再送**。しかも同じセッションは**使える顧客IDを持っている**のに、
壊れた値が truthy だったせいでそちらに落ちてこなかった。

**直した内容**: metadata は**手掛かり**として扱い、uuid の形をしていなければ捨てる
（捨てたことは `metadata_user_id_not_a_profile_id` としてログに出す）。
権威のある紐付けは `stripe_customer_id` — Stripe が発行し、create-checkout が保存したもの —
のままで、そちらの経路が配信を運ぶ。`supabase_user_id` を先に読む順序は変えていない。

### 1.12 【修正済み】create-checkout の 3 つ（プロトタイプ／無検査の書き込み／死んだ顧客ID）

**(a) プランがプロトタイプ経由で引ける。**

```
const PRICE_MAP: Record<string, string | undefined> = { light: …, standard: …, pro: … };
const priceId = PRICE_MAP[plan];
if (!priceId) return 400 「無効なプラン」
```

`PRICE_MAP["constructor"]` は `undefined` ではなく `Object`（プロトタイプ由来）で、**truthy**。
`{"plan":"constructor"}` は 400 のガードを素通りし、**実際に Stripe の顧客を作り**、
`profiles` に書き込んでから、セッション作成で落ちる。利用者には 400 ではなく
Stripe のエラー本文が入った 500 が返る。webhook は同じ時期に同じ理由で `Map` にしていたのに、
**隣のファイルはオブジェクトのままだった**。

直した内容: 許可プランは `Set` の `has()` で判定し、索引を引かない。
価格IDが未設定のときは「無効なプラン」ではなく、**シークレット名を添えた 500**
（`missing_price_env`）にした。前者だとダッシュボードの設定漏れを
フロントエンドの不具合として調べ始めることになる。

**(b) DB の読み書きの結果を見ていない。** プロフィール行の読み取りは
`const { data: profile } = ...` でエラーを捨てており、`stripe_customer_id` の書き戻しは
結果を丸ごと捨てていた。行が無い利用者でも**決済は通り**、そのあと webhook が
`no_profile_matched` で 3 日間再送して終わる（＝課金だけ取れてプランは付かない）。

直した内容: **行が読めなければ決済を始めない**（500）。書き戻しの失敗は**ログに出す**が
致命傷にはしない — セッションの metadata に利用者IDが載っているので webhook 側で
書き戻せるし、ここで失敗にすると利用者はボタンを押し直すしかなく、
**防ごうとしている顧客の重複をかえって確実に作る**。

**(c) `profiles.stripe_customer_id` は全部、閉鎖したアカウントのもの。**
決済会社をつなぎ直した日、保存済みの顧客IDは**新しいアカウントにとって他人**になる。
古いコードはそれをそのまま `checkout.sessions.create` に渡していたので、
`resource_missing` → 素の 500 → **やり直しても永久に同じ**。コードにも手順にも
「この列を消す」とはどこにも書かれていなかった。

直した内容: 使う前に顧客IDを検証し、決済会社が知らないIDは**「IDが無い」のと同じ扱い**にして
新しい顧客を作り、列を上書きする（削除済み顧客は `deleted: true` のオブジェクトで返るので
両方の形を見る）。それ以外のエラーは**そのまま投げ直す** — 通信断や鍵の誤りを
「顧客をもう 1 つ作る」に化けさせないため。

### 1.13 【修正済み】試用中・支払い遅延中の利用者が解約できない

```
const subs = await stripe.subscriptions.list({ customer: ..., status: "active", limit: 10 });
if (subs.data.length === 0) return 400 「有効なサブスクリプションが見つかりません」
```

`status: "active"` は「課金されている契約」と**同じ集合ではない**。試用中は `trialing`、
カードが通らなくなった直後は `past_due`、その次は `unpaid`。そのどれかの利用者が解約を押すと
**「有効なサブスクリプションが見つかりません」**と言われ、そのまま請求され続ける。
**請求は続いているのに契約は無いと言われる**のは、チャージバックの入口そのもので、
UI にはただのエラートーストとしてしか出ない。

**直した内容**: 一覧は `status: "all"` で取り、`active` / `trialing` / `past_due` / `unpaid` を
コード側で選ぶ。`incomplete`（初回の支払いが一度も確定していない）は**あえて外した** —
止める請求が無く、放っておけば期限切れになる。合わせて `limit` を 100 に上げた。
`"all"` を 10 件で取ると、大昔の解約済み契約でページが埋まって現役が隠れうる。

### 1.14 【要確認・未修正】支払い未確定（`incomplete`）での付与

`checkout.session.completed` は `session.payment_status` も、取得したサブスクリプションの
`status` も見ずにプランを付与している。3D セキュアの確認が終わっていないなど、
**初回の支払いが確定していない状態でも付与される。**

1.9 で `canceled` / `incomplete_expired` は塞いだが、**`incomplete` はあえて塞いでいない**。
塞ぐべきかどうかは「`incomplete` が期限切れになったとき、`customer.subscription.deleted` が
確実に飛ぶか」で決まり、それは Stripe のドキュメントで確かめる事柄で、
**この環境からは参照できない**。塞いで、かつ後続の `updated` が来なければ、
**払ったのにプランが付かない**利用者を作る。**推測で直さない**（§1.7 と同じ理由）。

§3 のテスト決済のときに、3D セキュアのテストカードで 1 件通して**実際の挙動を見て決めること**。

### 1.15 【未修正・要判断】1 人の顧客に複数のサブスクリプションが作れる

**これはオーナーの方針判断が要るので、あえて直していない。**

`create-checkout` は、既に契約中かどうかを**一切見ない**。`src/pages/Pricing.tsx` も
3 つのボタンを常に押せる状態で出す。つまり `light` の利用者が `pro` を押すと、
**同じ顧客に 2 本目の契約ができて二重に請求される**。webhook は新しい方で
`plan` と `stripe_subscription_id` を上書きするので、**1 本目はアプリから見えないまま
請求され続ける**。今それが回収可能なのは、`cancel-subscription` がたまたま
（`limit` の範囲で）全部を解約するからにすぎない。

ここから派生して 2 つ。

* **古い `deleted` が、まだ払っている契約のプランを剥がす。** `deleted` の分岐は
  `stripe_customer_id` だけで一致を見て、**どの契約が終わったのかを見ていない**。
  2 本あるうち古い方の解約で `plan = free` になる。
* **古い `updated` が、新しい方のプランを上書きする。** 1.9 の読み直しでは塞げない
  （古い契約自体は生きているため）。

**直さなかった理由**: 素直な修正は「契約中なら 2 本目の checkout を断る」だが、それは
**プラン変更そのものを塞ぐ**（正しい実装は Stripe のカスタマーポータル、あるいは
既存契約の品目差し替えで、これは不具合修正ではなく機能追加）。もう 1 つの
「`profiles.stripe_subscription_id` と一致する契約の更新しか適用しない」は §1.9 のとおり
別の副作用がある。**どちらを取るかはオーナーが決めること。**

**当面の運用**: 決済を再開したら、まず「1 顧客に 2 本以上の有効な契約が無いか」を
Stripe 側で定期的に見る。これはコードを触らずにできる。

## 2. ダッシュボード側の手順（オーナーがやる）

### 2.1 モードを決める

右上の**テストモード**トグル。テストと本番で、APIキー・価格ID・署名シークレットが**すべて別物**。
ここを混ぜるのが一番多い失敗。まずテストモードで通してから本番に移す。

### 2.2 商品と価格を 3 つ作る

**商品** → **商品を追加**。`light` / `standard` / `pro` の 3 つ。

- 料金体系: **継続（Recurring）** ← 買い切りにするとサブスクにならない
- 請求期間: 月次
- 通貨: JPY

作成後、各価格の **`price_` で始まる ID** を控える。商品ID（`prod_`）ではなく**価格ID**。

**確認**: 商品一覧で 3 つとも「継続」と表示されていること。

### 2.3 Webhook エンドポイント

**開発者** → **Webhook**。

- URL: `https://endcqzewujdvimdlazhj.supabase.co/functions/v1/stripe-webhook`
- イベント（現行コードが処理するのはこの 3 つだけ。増やしてもコード側が無視する）
  - `checkout.session.completed` … 初回契約でプランを上げる
  - `customer.subscription.updated` … プラン変更を反映する
  - `customer.subscription.deleted` … 解約で `free` に戻す

登録後に表示される**署名シークレット（`whsec_` で始まる）**を控える。

**確認**: エンドポイントが「アクティブ」で、リッスン対象が 3 件。

### 2.4 Supabase にシークレットを 5 つ入れる

Supabase ダッシュボード → **Edge Functions** → **Secrets**。
**名前がこの通りでないと動かない**（コードが `Deno.env.get` で読む名前）。

| 名前 | 値 |
|---|---|
| `STRIPE_SECRET_KEY` | `sk_test_...` または `sk_live_...` |
| `STRIPE_WEBHOOK_SECRET` | §2.3 の `whsec_...` |
| `STRIPE_PRICE_LIGHT` | ライトの `price_...` |
| `STRIPE_PRICE_STANDARD` | スタンダードの `price_...` |
| `STRIPE_PRICE_PRO` | プロの `price_...` |

**値をチャットや git に貼らないこと。** ダッシュボードで直接入力する。

**確認**: この 5 つは、このセッションからは**読めない**。入力したことはオーナーしか確認できない。

## 3. つながったことの確かめ方

§1 を直して再デプロイし、§2 を終えてから、テストモードで 1 件通す。

1. アプリから購入 → Stripe のテストカード `4242 4242 4242 4242` で決済
2. Stripe の **Webhook** → 該当エンドポイント → **イベントの配信** で
   `checkout.session.completed` が **200** で配信されていること
3. データベースで、その利用者の行が上がっていること

```sql
select plan, stripe_customer_id is not null as has_customer,
       stripe_subscription_id is not null as has_subscription, updated_at
from public.profiles where id = '<user_id>';
```

`plan` が `light` / `standard` / `pro` のいずれかになり、`has_subscription` が `true` なら成功。
`free` のままなら §1.1 の修正が入ったビルドをデプロイできていない。

**修正後は、失敗が「失敗」として見えるようになっている。** 設定漏れがあると配信が
**500 で失敗**し、Stripe が自動で再送する（以前は黙って 200 を返していた）。
配信画面のレスポンス本文に理由が入っているので、そこを読む。

| レスポンスの `error` | 状態 | 意味 | 直し方 |
|---|---|---|---|
| `signature_verification_failed` | 400 | 署名が合わない | `STRIPE_WEBHOOK_SECRET` が別エンドポイントのものか、モード違い（§2.1） |
| `missing_required_env` | 500 | 必須シークレットが未設定 | 一緒に出る `missing`（**名前だけ**）を §2.4 で入れる |
| `unknown_price_id` | 500 | 価格IDが対応表に無く、シークレットも未設定 | 一緒に出る `missing_price_env` を §2.4 で入れる |
| `db_update_failed` | 500 | DB の書き込みが失敗 | **本文には理由を入れていない。** Supabase の Edge Function のログの `db_error` を見る |
| `no_profile_matched` | 500 | 対象の利用者の行が見つからない | `profiles.stripe_customer_id` の紐付けを確認 |

400 だけは**再送されない**（署名が合わない本文は何度送っても合わないため）。
それ以外の失敗は、原因を直せば Stripe の再送で自動的に通る（およそ 3 日間）。

**レスポンス本文に入れるのは、環境変数の「名前」までにしている。** Stripe は
レスポンス本文を配信ごとに保存してダッシュボードに表示する。Postgres のエラー文は
違反した**値そのもの**を引用することがあるので、それをそのまま返すと
行の中身を他社の画面に書き出すことになる。診断に必要な情報は
**Edge Function のログ側**に全部出ている（`event_id` で突き合わせる）。

**200 で返るのに問題があるものが 1 つだけある。** `unknown_price_id_not_retryable`
（§1.3）は「対応表は揃っていて、単にうちの価格IDではない」場合で、再送では直らないので
200 で終える。この状態は**課金は取れてプランは付与されていない**ので、
`console.error` の行を**監視対象に入れること**。

**逆に、失敗が続きすぎるのも危険**なので覚えておく。Stripe は失敗の続く
エンドポイントに通知を出し、最終的に無効化する。無効化されれば全員分の付与も剥奪も止まり、
**また静かになる**。本番に出した後しばらくは、配信の失敗率を見ておくこと。

4. 解約 → `customer.subscription.deleted` が 200 で配信され、`plan` が `free` に戻ること

`public.profiles` の `plan` は `profiles_plan_check` で
`free` / `light` / `standard` / `pro` のみ許可されている。他の値を書こうとすると制約で落ちる。
