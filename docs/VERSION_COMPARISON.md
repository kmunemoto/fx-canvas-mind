# 候補ルールブックの比較（#65）— 何が言えて、何が言えないか

この文書は**専門家でないオーナー向け**に書いてある。数式は最後にまとめてあり、読まなくても
判断はできる。**まだ 1 回も課金される呼び出しをしていない状態で書いた。**

一次資料はコードのコメントで、この文書はその索引である。行番号ではなくシンボル名で引く。

- 比較ハーネス: `supabase/functions/version-compare/index.ts`
- 判定の算数: 同ディレクトリの `mcnemar.ts`（検定と必要行数）と `pairing.ts`（どのスナップショットが
  どの段階に使えるか、答えの組をどう突き合わせるか）
- 表: `supabase/migrations/20260910180000_freeze_the_candidate_before_measuring_it.sql`
- 土台になっているノイズ測定: `docs/NOISE_FLOOR_PREREGISTRATION.md`

## 0. 一言でいうと

**今日わかるのは「候補ルールブックに変えると、アナリストの答えがどれくらい変わるか」だけである。
「候補のほうが儲かるか」は今日はわからないし、今ある過去データを何回なめても永久にわからない。**

わかるようにするには、**候補を凍結したあとに新しく生まれたスナップショットを 75 件**ためて、
そこで初めて成績を比べる。それが下の「段階B」である。

---

## 1. なぜ「まず凍結する」のか

`public.rulebook.candidate`（候補ルールブック）は、postmortem 関数が **おおよそ 6 時間ごとに
丸ごと書き換えている**。実測（2026-09-10、本番）:

- 現行（live）はバージョン 8、ルール 3 件
- 候補はルール 4 件、`base_version` 8、`created_at` 2026-09-10T05:53:53Z
- `candidate->superseded` に**過去 5 世代**が積まれている

比較の実行には数時間かかる。凍結しなければ、**最初の 1 件と最後の 1 件で別のルールブックを測って
いる**ことになり、しかも記録にはどの行がどの世代のものだったかが残らない。全部が「測定」に見える。

だから比較の実行は「候補」を指さない。**凍結 ID** を指す。凍結行はコピーであり、
トリガーで UPDATE も DELETE も拒否される（RLS では止められない。この表に触れるのは
service_role だけで、service_role は RLS を素通りするから、止められるのはトリガーだけである）。

**現行側も同時に凍結する。** 現行ルールブックも postmortem が候補を昇格させれば動く。片側だけ
凍結すると、午前中はバージョン 8 と比べ、午後はバージョン 9 と比べることになる。それは 2 つの
実験を 1 つとして報告することである。

操作: `{"action":"freeze"}` を投げると凍結行ができる。**モデルは 1 回も呼ばれない（無料）。**
同じ内容の凍結が既にあれば、新しく作らずにその ID を返す。

## 2. 段階A（Materiality / 有意味性）— 今日できること

### やること

保存済みのスナップショット 1 件につき、**同じ市場・同じ質問**を 2 回投げる。

- **live 腕**: 保存されたプロンプトの「学んだルール」ブロックを、凍結した**現行**ルールブックに差し替える
- **candidate 腕**: 同じプロンプトの同じ場所を、凍結した**候補**ルールブックに差し替える

そして **2 つの答えが食い違った回数だけ**を数える。

### なぜこれは安全なのか

**結果（勝った・負けた）を一切読まない。** 読まないものは漏れようがない。

### 何と比べるのか

`docs/NOISE_FLOOR_PREREGISTRATION.md` で測った**同じルールブック同士の食い違い率**と比べる。
実測: **48 行中 10 行、20.83%、Wilson 95% 区間 [11.73%, 34.26%]**。

つまり、**このアナリストは何も変えなくても 5 回に 1 回は別の結論を出す**。しかもそれは
「SELL 確信度 66」対「WAIT 確信度 45」という規模の別れ方で、床際の小さな揺れではない。

判定は 3 つしかない:

| 判定 | 条件 | 意味 |
|---|---|---|
| `material` | 今回の食い違い率の**下限**が、ノイズ床の**上限** 34.26% を超えた | 変化は本物に大きい。段階Bに金を払う価値がある |
| `indistinguishable` | 2 つの区間が重なった | **何も示せていない。**「同じだ」ではない |
| `below_floor_investigate` | 今回の**上限**がノイズ床の**下限**を下回った | ルールブックの話ではない。道具のほうが #64 のときと変わっている疑い |

**点推定ではなく区間で比べている**理由は、ノイズ床そのものが幅 22 ポイントの推定値だからである。
20.83% を「わかっている数」として扱うと、ノイズ測定のブレでルールブックを昇格させてしまう。

### 段階Aがどれくらい**大きな**変化なら見えるのか（重要）

保守側に倒した代償として、**この選別はかなり大きな変化しか検出できない**。

`material` を出すには、今回の食い違い率の下限がノイズ床の上限 **34.26%** を超えないといけない。
ノイズ床が 48 行でしか測れていないので、この上限が高いのである。逆算すると:

| 今回の行数 | `material` を出すのに必要な食い違い | 割合 |
|---|---|---|
| 78 行（現在の corpus） | 35 行 | **約 45%** |
| 156 行 | 66 行 | 約 42% |
| 300 行 | 119 行 | 約 40% |

つまり **78 行では「アナリストの答えの半分近くを書き換えるルールブック」でないと `material` にならない。**
候補が答えの 2 割を変える程度なら `indistinguishable` が出る。そのとき出ているのは
**「候補は何もしない」ではなく「この選別ではこの大きさの変化は見えない」**である。

この数字は報告の JSON にも `smallest_material_disagreement` として毎回入る。
導出させるのではなく、書いて出す。

### 段階Aが**言えないこと**

**「候補のほうが良い」とは絶対に言えない。** 全部の答えを悪いほうに変えるルールブックは、
この指標で**満点**を取る。段階Aは「差が大きいか」しか見ておらず、「差の向き」は見ていない。

これはコードにも書いてある。API の返り値そのものに次の一文が入る:

> `a screening test on how often the two books disagree; it is NOT evidence that either book is better`

## 3. 段階B（Performance / 成績）— 今日は絶対にできないこと

### なぜ過去のスナップショットが使えないのか

**候補ルールブックは、まさにその過去のトレードから作られている。**

実測（2026-09-10）:

- `candidate->>'lessons_considered'` = **60**
- この 60 は postmortem の `RECENT_LESSONS` という**上限値**であって「表の全部」ではない
  （凍結時点で lessons は 75 件、現在 78 件）
- lessons 78 件のうち **60 件**は、`public.analysis_prompts` にプロンプトが保存されている
  分析についてのものである

つまり、**再生に使える過去データと、候補が学習に使ったデータは、ほぼ同じ行**である。

その過去行で候補を採点するのは、答えを見せてから試験を受けさせるのと同じである。候補は必ず良く
見える。良く見えたことは何の証拠にもならない。これを **リーク（leakage）** という。

### だから、こうする

段階Bに使えるのは **凍結時刻より後に生まれたスナップショットだけ**。その行については、候補は
「予測」をしていることになる。

この足切りは **4 か所で強制している**。忘れようがないようにするためで、口約束ではない。

1. **クエリの中**: PostgREST に `created_at=gt.<凍結時刻>` を送っている。あとから TypeScript で
   絞るのではない（あとから絞る実装は、リファクタで消えてもテストが全部通ってしまう）
2. **純関数**: `pairing.ts` の `eligibleForStage` が同じ規則を独立に述べ、クエリと食い違えば
   実行を**拒否**する
3. **データベースのトリガー**: 移行ファイルの `version_compare_runs_respect_the_split`
4. **報告のとき、もう 1 回**: 上の 3 つは全部「実行を**作る**とき」の検査である。実際に数字を
   出すのは報告モードで、そこが採点する行を決めているのは実行ヘッダの `notes.population.ids`
   という列であり、**トリガーはその列を見ていない**（`notes` はリースと封印で書き換わるので、
   意図的に監視対象から外してある）。だから報告モードは、採点しようとしている行の
   `created_at` を**読み直して**、凍結時刻より後であることを確かめてから、初めて結果を読む。
   1 行でも確認できなければ**報告そのものを拒否**する（`stage_b_population_not_forward_only`）

4 番目はレビューで見つかった穴である。それまでは「作るときは 3 重に守られているが、
**数字を出す経路には 1 つも検査がない**」という状態だった。将来だれかが「母集団を広げる」
機能を足したら、トリガーは黙ったまま、テストも全部通ったまま、候補が学習した行の上で McNemar が
回り、その JSON には「候補はこれらの行について何も学んでいない」と書かれていたはずである。

なお報告モードが使う下限は、**実行が宣言した下限と凍結時刻そのものの、遅いほう**である。
移行ファイルをまだ適用していないデータベース（＝トリガーが存在しない状態）でも成立させるため。

なお境界は**「凍結時刻より厳密にあと」**である。同じミリ秒に書かれた行は、記録からは前後関係が
決められない。決められないものは使わない。

### 採点のしかたと、その弱点

腕の答えは「トレードした（traded）」か「見送った（waited）」の 2 つだけ。市場の答えは 2 つの
情報源から取る:

| 情報源 | 条件 | 市場の答え |
|---|---|---|
| `analyses.outcome` | `win` | トレードが正しかった |
| `analyses.outcome` | `loss` | 見送りが正しかった |
| `analyses.wait_check.verdict` | `missed` | トレードが正しかった |
| `analyses.wait_check.verdict` | `correct` | 見送りが正しかった |
| それ以外（`untriggered` / `pending` / `no_call` / `unknown`） | — | **採点できない。行を落とす** |

**ここが設計の一番弱い環である。正直に書く。**

- 腕の答えには**損切りも利確も含まれていない**。「トレードが正しかった」と採点するとき、
  「その腕も本番と同じ水準でトレードしたはずだ」と仮定している。**この仮定は検証していない。**
  損切り幅を広げるようなルールが候補に入っていれば、判断は同じでも結果は変わりうる
- 2 つの情報源は**別のコードが測った別の反実仮想**である。行ごとにどちらで採点したかは記録し、
  報告にも件数を出す
- 実測（2026-09-10）で、プロンプトが保存されている 78 行のうち採点可能なのは
  win 21 + loss 14 + wait_check の correct/missed 分だけ。**採点できない行はかなり多い**

### 判定のしかた

食い違ったペアだけを数える（両方正解・両方不正解のペアは、どちらが良いかについて何も語らない）。

- **b** = 現行が正解・候補が不正解
- **c** = 現行が不正解・候補が正解

これに**厳密二項検定（McNemar）**をかける。カイ二乗近似は使わない。この harness が数週間で
到達しうる食い違いペア数は 1 桁で、その領域では近似がずれ、しかも**ルールブックを昇格させる
向きにずれる**。

## 4. 段階Bには何行必要か

事前登録した設計（`docs/NOISE_FLOOR_PREREGISTRATION.md` §4）は Δ=0.20、両側 α=0.05、検出力 80%。
**ノイズは検定を偏らせないが、薄める。**だから必要な行数はノイズ率とともに増える。

実測ノイズ床 20.83% を入れると:

> ψ = 0.744918、K = 1.346851、n = 74.07 → **対応ペア 75 行**

**凍結後に生まれたスナップショットが 75 組そろうまで、段階Bは何も言えない。**

現状の観測ペース（`analysis_prompts` は 2026-09-09 に 48 行、2026-09-10 に 78 行。1 日 15〜30 行）
なら、**おおよそ 3〜5 日**。ただしこれは「毎日同じペースで、すべての行が採点可能なら」という
話であって、上に書いたとおり**採点できない行がかなり出る**ので、実際にはもっとかかる。
**この所要日数は見積もりであって測定ではない。**

参考（同じ式で計算し直した数字）:

| ノイズ床 p₀ | 必要な対応ペア |
|---|---|
| 0%（正確計算） | 39 |
| 5% | 38 |
| 10% | 51 |
| **20.83%（実測）** | **75** |
| 30% | 94 |
| 50% | 134 |

そして、**食い違いペアが 6 組未満だと、どんな結果が出ても統計的には何も言えない**
（両側の厳密二項検定が 0.05 に届く最小が m=6。2×0.5⁶=0.03125）。報告は `underpowered: true` と
書いて出す。「検定して差がなかった」と「検定ができなかった」を同じ顔で出さないためである。

### 75 行そろって「差なし」と出たとき、それは「候補は良くない」ではない

ここは読み間違えやすいので、はっきり書く。

この設計の Δ=0.20 は**非常に大きな効果**である。ψ = 0.7449 という数字が意味するのは、
**「食い違ったペアの約 74.5% を候補が取る」ほど強い候補**でないと、75 行では検出力 80% に
届かないということである。

したがって:

> **75 行で `significant: false` が出ても、それは「候補は良くなかった」ではない。
> 「事前登録した幅（食い違いペアの 74.5%）ほどは良くない」というだけである。**
> 本当に少しだけ良い候補は、この設計では必ず「差なし」に見える。

報告の JSON にも `not_significant_means` として同じ一文が入る。

### いつ見るか（optional stopping を塞ぐ）

報告は**無料で何度でも実行できる**。しかも母集団を固定したままでも、時間が経てば結果が確定して
**採点できるペアは増えていく**。ここに規則がないと、3 日目（72 ペア、結論なし）、5 日目
（78 ペア、p=0.09）、8 日目（84 ペア、p=0.04）と見て、**一番良かった日を発表できてしまう**。
これを optional stopping といい、こうすると名目 5% は 5% ではなくなる。

だから規則を 1 つ決めてある:

> **事前登録した 75 ペアに到達した「最初の 1 回」が検定である。**

その 1 回は `version_compare_runs.stage_b_seal` 列に封印される。以後の報告も数字は出すが
`post_hoc_recount: true` が付き、**`conclusive` は封印された 1 回からしか取らない**。
封印列はトリガーで**上書き不可**にしてある（関数側の条件付き UPDATE と DB の二重）。
75 ペア未満の回は、そもそも `conclusive` になれないので「検定」ではない。

### 採点の内訳を必ず出す

`b` と `c` は**情報源ごとにも**出す（`by_truth_source`）。理由は、どちらの情報源が付くかが
**現行腕の判断と相関している**からである。`outcome` は本番がトレードした行にしか無く、
`wait_check` は見送った行にしか無い。候補が判断を一方向にずらすと、食い違いペアが片方の情報源に
偏り、p 値が「ルールブックの差」ではなく「その情報源の較正」に乗ってしまう。
まとめた `b`/`c` からは後で分解できないので、最初から分けて出す。

**この内訳は感度チェックであって、追加の検定ではない。** 3 つのうち一番小さい p 値を選んで
発表したら、それは 3 回検定して 1 回だけ報告したということである。事前登録した検定は
**まとめたほうの 1 回だけ**である。

## 5. 検証していないこと（overclaim しないために）

ここは飛ばさずに読んでほしい。**この設計が正しいかどうかは、以下の未検証事項に依存している。**

1. **両方の腕を描き直している。** 保存されたプロンプトのルールブロックは「順位付き」で描かれて
   おり、各ルールに「今の相場に該当／今は別局面／今との照合不可」という**そのときの相場と
   比べた印**が付いている。候補のルールにはその印を作れない（別の過去局面から作られたルールなので、
   今日計算し直せば「今日の相場」と比べたことになってしまう）。

   そこで **live 腕も candidate 腕も、印なしで描き直している**。こうすると 2 つの腕の違いは
   「ルールの中身」だけになり、対応比較（ペアリング）が成立する。

   **代償: どちらの腕も、本番が実際に送ったバイト列とは違う。** したがって段階Aが測っているのは
   「印なしの描き方のもとで、ルールを入れ替えると答えが変わるか」であって、「本番の答えが
   変わったはずか」ではない。

   **そして 20.83% というノイズ床は、印ありの保存バイト列で測った数字である。**
   印なしのプロンプトでもノイズ率が同じである保証は**ない。未検証**。確かめるには
   印なしプロンプトでノイズ測定をもう 1 回（96 回の課金呼び出し）走らせる必要がある。

   **ずれる向きまで書いておく。**「同じか違うか不明」で止めるのは不誠実なので言うと、
   印なしのほうがノイズ率は**高くなりうる**。取り除いた印（「今の相場に該当」など）は
   確信を持たせる文言で、いくつかのルールを「今は別局面」と固定していたからである。
   もし印なしの本当の床が 20.83% より高いなら、

   - 段階Aは**低すぎる床**と比べていることになり、`material` が出やすいほうに偏る
   - 段階Bの必要行数 75 は**少なすぎる**見積もりということになる

   どちらも**ルールブックを昇格させる向きの偏り**である。だから「不明」ではなく
   「この向きに偏りうる」と書く。

2. **web 検索を外している。** 両腕とも `tools` なし。#64 の主アームと同じで、比較は「再生 対 再生」
   なので内部妥当性は保たれるが、**本番の経路（検索あり）でも同じ数字になる保証はない**。

3. **段階Bの採点仮定**（§3 の「一番弱い環」）。腕の答えに水準が含まれていないこと。**未検証**。

4. **母集団が狭い。** 実測で通貨ペアは 1 種（USD/JPY）、アカウントは少数、期間は数日。
   読める主張は「これらのスナップショットについて」だけである。

5. **`lessons_considered = 60` は「表の全部」ではない。** これは設計の前提として渡されていたが、
   本番を数え直すと 60 は上限値で、凍結時点の lessons は 75 件だった。リークの結論は変わらない
   （60 件のうち大半が再生対象の分析についてのものだから）が、**理由が違うので直した**。

## 6. お金の話

このハーネスは**呼ぶたびに課金される**。しかも本番アプリの分析と postmortem と**同じ API キー**
を使う。2026-09-08 には、そのキーの残高切れで実利用者の画面にエラーが出ている。

だから制御は「警告」ではなく「拒否」にしてある。すべて noise-floor からそのまま持ってきた:

- `dry_run` は**既定で true**。フィールドを書き忘れても、綴りを間違えても、そもそも JSON でなくても
  無料の経路に落ちる。**明示的な `false` だけ**が課金経路に届く
- 課金する実行は、**完了した dry run なしには作れない**。予算 2 本は dry run が実測した数字から
  選び、その 2 倍を超える予算は**拒否**される（psql のヒアドキュメントでゼロを 1 個多く打つと
  桁が 1 つ増えるので）
- 1 回の呼び出しで扱えるセル数はサーバ側で上限 4
- 支出は「呼び出し回数」ではなく毎回の `usage` から**実測**する。加えて、**測れなかった支出は
  ゼロとして扱わない**（タイムアウトした呼び出しは請求されるのに usage が返らない）
- 呼び出しは**厳密に直列**、しかも**前の呼び出しが終わってから 20 秒**空ける。これは
  「以前のハーネスがエッジワーカーを 40 分占有し、実利用者の分析が 1 件つながらなかった」
  という実測から来た数字である
- pg_cron が動く 9 つの分（3, 8, 13, 18, 23, 33, 38, 48, 53）には**セルを開始しない**し、
  **その分にまたがって走りもしない**
- 1 つの dry run が認可できる課金実行は 1 つだけ（関数側の検査と、DB の部分ユニーク索引の二重）
- 401 / 403 / 429 と残高エラーは**リトライしない。実行ごと止める**

**pg_cron に登録してはいけない。**このジョブは存在しないし、作ってもいけない。操作者が SQL から
手で叩く。トークンは vault から SQL の中で読み、値はどこにも書き残さない。

## 7. 実行手順（要約）

すべて `x-sweep-token` ヘッダ付きの POST。**この順番以外では課金経路に到達できない。**

1. **凍結**（無料）: `{"action":"freeze"}` → `freeze_id` が返る
2. **試算**（無料）: `{"freeze_id":"…","stage":"materiality"}` → 入力トークンの実測値と
   出力トークンの上限が返る。`dry_run` は書かなくてよい（既定で true）
3. **実行**（課金）: `{"dry_run":false,"dry_run_id":"…","stage":"materiality",
   "budget_input_tokens":N,"budget_output_tokens":M,"chain":true}`
   — N と M は 2 で見た数字から選ぶ
4. **続き**: `{"dry_run":false,"run_id":"…","chain":true}`
5. **止める**: `version_compare_runs` の `status` を `paused` に UPDATE する。次の hop が読んで止まる
6. **報告**（無料）: `{"report_run_id":"…"}` — 全セルが揃うまで**数字を出さない**

段階Bは 1 と 2 のあいだに時間を空ける。凍結直後に `stage:"performance"` で試算すると、
**「凍結以降に書かれたスナップショットが 1 件もない」と拒否される。**それが正しい動作である。

### 手間の実測見積もり（始める前に知っておくこと）

**手順 2（試算）は思ったより回数が要る。** 現在の 78 行 × 2 腕 = **156 回**の `count_tokens`
（無料）が必要で、これも 20 秒間隔・1 回の呼び出しあたり 6 件程度なので、
**手動 POST が 26 回**くらいになる。しかも**試算は自動で次の hop を呼ばない**（`chain` なし）。
noise-floor が 8 回程度で済んだのは、あちらの 2 本の腕がバイト単位で同一で、行ごとに 1 回だけ
数えれば足りたからである。こちらは 2 本の腕の中身が違うので、行ごとに 2 回数える必要がある。

もう 1 つ。プロンプトが `technical_fallback` の行が 1 つでも混じると、試算は永久に
`complete: false` のままになり、**課金実行を作れなくなる**。現在の 78 行の内訳は
full 75 / technical_only 3 / technical_fallback **0** なので今は起きないが、これは
「今のデータがそうだ」というだけで保証ではない。**止まる向きに壊れる**設計ではあるが、
起きたときはバグに見えるので、先に書いておく。

## 8. レビューで出た指摘と、その処理

3 人のレビュー（リーク、支出、スコープ）で出た指摘を全部ここに書く。**直したもの**と
**直さないと決めたもの**を、同じ表に並べる。直さなかったものを隠さないためである。

### 直したもの

| 指摘 | 何が起きえたか | 対応 |
|---|---|---|
| **報告経路に足切りが 1 つも無い**（最重要） | 将来の機能追加や手書きヘッダで `notes.population.ids` に凍結前の行が入ると、トリガーは黙ったまま、テストも全部通ったまま、**候補が学習した行の上で McNemar が回る** | 4 番目の錠を追加（§3）。採点直前に `created_at` を読み直し、1 行でも怪しければ**報告ごと拒否** |
| **停止規則が無い**（optional stopping） | 報告は無料で何度でもでき、採点可能ペアは日々増える。一番良かった日を発表できてしまい、名目 5% が 5% でなくなる | 75 ペアに到達した最初の 1 回を `stage_b_seal` 列に封印。以後は `post_hoc_recount`。列はトリガーで上書き不可（§4） |
| **b/c を 2 つの情報源で混ぜていた** | 情報源は現行腕の判断と相関しているので、p 値が「ルールブックの差」ではなく「片方の情報源の較正」に乗りうる。しかもまとめた b/c からは後で分解できない | `by_truth_source` として情報源別の b/c と検定を併記（感度チェックであって追加の検定ではないと明記） |
| **「75 行で差なし」の読み違いを止める文が無かった** | オーナーが「候補は良くなかった」と読む。実際は「食い違いペアの 74.5% を取るほどには良くない」でしかない | §4 に節を追加。JSON にも `not_significant_means` |
| **段階Aが実際どれだけ大きな変化しか見えないか書いていなかった** | `indistinguishable` を「候補は何もしない」と読む。実際は 78 行だと**約 45%** の食い違いが必要 | §2 に逆算表を追加。JSON にも `smallest_material_disagreement` |
| **中断がオペレータの `paused` を上書きしうる** | 実行中に停止スイッチを引いた記録が、ワーカー側の `aborted` で消える（支出は増えないが記録が消える） | 状態更新を `status=eq.running` 条件付きに統一 |
| **呼び出し間隔 20 秒が hop をまたぐと効いていなかった** | 1 hop に課金セルが 1 件しか入らないので、**課金呼び出しのほぼ全部が「その呼び出しの 1 回目」**になり、実際の間隔は数秒だった。共有 API キーに対する保証が守られていなかった | 親が最後の呼び出し終了時刻を子に渡す。さらに間隔スリープを**壁時計チェックの前**に移動（後だと 80 秒あると判断して寝てから 60 秒しか残らない） |
| **pause 継続のタイムアウトが古い残り時間で計算されていた** | 20 秒寝てから満額のタイムアウトを与えることになり、締切と書き込み予備を食う（現在の設定では到達不能だが、算数は間違っていた） | スリープの**後**に計算し直す |
| **ja が同一・en が違う 2 冊が 500 になっていた** | 凍結の同一性は ja のダイジェストで決まるので制約違反になる。関数側には明確な拒否文があるのに、不透明な 500 が返っていた | ja が同一なら**拒否文で返す**（どちらの言語で潰れたかも書く） |
| コメントの参照名が古い（`readFrozenIds`）／トリガーの説明文が実装より厳しく書いてあった | 仕様書として読まれると誤解のもと | 両方修正。**「凍結より遅い下限は受け入れる」**（行を捨てる向きなので安全）と明記 |

### 直さないと決めたもの

| 指摘 | なぜ直さないか |
|---|---|
| **試算（dry run）経路にリースが無い** | 同じ ID で 2 回同時に叩くと、無料の `count_tokens` が二重に走り、間隔も守られない。ただし**無料**で、オペレータが二重に叩かない限り起きず、noise-floor の試算経路も同じ形。コードにコメントとして残した |
| **ミリ秒とマイクロ秒の精度差** | `Date.parse` はミリ秒、Postgres はマイクロ秒で比較する。凍結と同じミリ秒・後のマイクロ秒に書かれた行はクエリを通り純関数で落ちる。ただし**食い違いは実行の拒否**になるので、漏れるのではなく止まる。安全な向き |
| **試算に手動 POST が 26 回必要** | 設計上の手間であってバグではない。§7 に見積もりとして書いた |
| **段階Bの採点に水準（損切り・利確）が入っていない** | これは設計の限界そのもので、直すには腕に実際の建玉計画を出させて別に検証する必要がある。**この設計の一番弱い環**として §3 と §5 に書いてある |
| **印なし描き直しのノイズ床が未測定** | 測るには 96 回の課金呼び出しがもう 1 回要る。偏る向きまで §5 に書いた |

### この文書を書いた時点で**やっていないこと**

- **データベースに対して 1 度も実行していない。**移行ファイルは書いただけで、適用していない
- したがって PostgREST の経路（リースの条件式、`on_conflict`、封印列の条件付き UPDATE）は
  **一度も通していない**。綴りが違えば最初の呼び出しが 500 で落ちるだけで、**支出は発生しない**。
  間違うならその向きで間違うようにしてある
- モデルは 1 回も呼んでいない。段階Aの数字も段階Bの数字も、**まだ 1 つも存在しない**

## 9. 数式（読まなくてよい）

事前登録（`docs/NOISE_FLOOR_PREREGISTRATION.md` §4）のものをそのまま使っている。

    ψ = 1/2 + (Δ/2)/(Δ + p₀)
    K = z_{α/2}/2 + z_β·√(ψ(1−ψ))
    n = 4K²(Δ + p₀)/Δ²

Δ = 0.20、z_{α/2} = 1.959964、z_β = 0.841621。p₀ = 0 ではこの式が壊れる（ψ が 1 になって
√ の項が消え、n が 20 まで落ちる）ので、そこだけは正確計算の **39** を使う。実装は
`mcnemar.ts` の `requiredPairs` で、`src/test/version-compare.test.ts` が上の表を 1 行ずつ
突き合わせている。どちらかが動けばテストが落ちる。

McNemar の厳密二項検定は m = b + c として

    p = min(1, 2 · P(X ≤ min(b,c)))    ただし X ~ Bin(m, 1/2)

二項係数は 1 度も作らない（`C(200,100)` は約 9×10⁵⁸ で、先に作ると桁が落ちる）。
0.5^m から確率質量を掛け算で進める。
