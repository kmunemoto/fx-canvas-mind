## 0. 一言でいうと

**今日わかるのは「候補ルールブックに変えると、アナリストの答えが『同じ本をもう一度引いたとき』より
大きく変わるか」だけである。「候補のほうが儲かるか」は今日はわからないし、今ある過去データを
何回なめても永久にわからない。**

わかるようにするには、**候補を凍結したあとに新しく生まれたスナップショット**をためて、そこで初めて
成績を比べる。それが下の「段階B」である。

### 2026-09-10 の設計変更（これが今の版の中身）

前の版は「食い違い率」を **#64 が測った 20.83% という定数**と比べていた。**その比較は成立していなかった。**
20.83% は**保存されたバイト列**（ルールが順位付きで、各ルールに「今の相場に該当」等の印が付いている）で
測った数字である。ところがこのハーネスは、候補のルールにその印を作れないので、**両方の腕を印なしで
描き直している**。つまり、測っている数字と比べている床が**別の形のプロンプトから来ていた**。

そこで**腕を 3 本にした**。同じ行・同じ描き方・同じ日に、床を**実測**する。

| 腕 | 中身 |
|---|---|
| `live` | 凍結した**現行**ルールブック、印なしで描き直し（基準） |
| `candidate` | 凍結した**候補**ルールブック、印なしで描き直し |
| `live_b` | 凍結した**現行**ルールブックを**もう一度**、`live` とバイト単位で同一のリクエスト（**対照**） |

`live_b` と `live` の食い違いは、**同じ本が自分自身と食い違う率**である。これが床であり、
借り物ではなく測ったものである。**費用はおよそ 1.5 倍になる。**オーナーはそれを払うと決めた。

## 1. なぜ「まず凍結する」のか

`public.rulebook.candidate`（候補ルールブック）は、postmortem 関数が **おおよそ 6 時間ごとに
丸ごと書き換えている**。実測（2026-09-10、本番）:

- 現行（live）はバージョン 8、ルール 3 件
- 候補はルール 4 件、`base_version` 8、`created_at` 2026-09-10T05:53:53Z
- `candidate->superseded` に**過去 5 世代**が積まれている

比較の実行には数時間かかる。凍結しなければ、**最初の 1 件と最後の 1 件で別のルールブックを測って
いる**ことになり、しかも記録にはどの行がどの世代のものだったかが残らない。全部が「測定」に見える。

だから比較の実行は「候補」を指さない。**凍結 ID** を指す。凍結行はコピーであり、
トリガーで UPDATE も DELETE も拒否される（RLS では止められない。この表に触れるのは
service_role だけで、service_role は RLS を素通りするから、止められるのはトリガーだけである）。

**現行側も同時に凍結する。** 現行ルールブックも postmortem が候補を昇格させれば動く。片側だけ
凍結すると、午前中はバージョン 8 と比べ、午後はバージョン 9 と比べることになる。それは 2 つの
実験を 1 つとして報告することである。

操作: `{"action":"freeze"}` を投げると凍結行ができる。**モデルは 1 回も呼ばれない（無料）。**
同じ内容の凍結が既にあれば、新しく作らずにその ID を返す。

## 2. 段階A（Materiality / 有意味性）— 今日できること

### やること

保存済みのスナップショット 1 件につき、**同じ市場・同じ質問**を **3 回**投げる。

- **live 腕**: 保存されたプロンプトの「学んだルール」ブロックを、凍結した**現行**ルールブックに差し替える
- **candidate 腕**: 同じプロンプトの同じ場所を、凍結した**候補**ルールブックに差し替える
- **live_b 腕（対照）**: `live` と**まったく同じリクエストをもう一度**投げる

**3 つを投げる順番は行ごとに入れ替える。** 1 hop でだいたい 1 セルしか買えないので、
宣言順に投げると「候補との比較はいつも 1 区間ぶん、対照との比較はいつも 2 区間ぶん」離れることになり、
実行中の配信経路の揺れが**対照側にだけ系統的に乗る**。6 通りの並びを (run_id, analysis_id) の
ハッシュで 1 つ選ぶことで、両方の間隔の期待値が等しくなる（§5-3）。
ハッシュであって乱数ではないのは、hop ごとに pending を組み直すからである。

1 行につき 2 つの「食い違ったか」が取れる。

- **D_cand** = candidate が live と違う答えを出したか
- **D_ctrl** = live_b が live と違う答えを出したか（＝**同じ本が自分自身と食い違ったか**）

### なぜこれは安全なのか

**結果（勝った・負けた）を一切読まない。** 読まないものは漏れようがない。

### 何と比べるのか — **借り物の定数ではなく、この実行が測った床**

**D_ctrl の率が床である。**同じ行・同じ描き方・同じ日に測ったものなので、「比べているものが
別の形のプロンプトから来ている」という問題が消える。

質問はこうなる:

> **ルールブックを入れ替えると、同じルールブックをもう一度引いたときより、答えは大きく動くか。**

### 検定 — 対応のある McNemar

D_cand と D_ctrl は**同じ行から取った 2 つの観測**なので、対応がある。だから区間どうしを比べるのでは
なく、**行ごとに突き合わせる**。食い違いペアの定義（**ここを逆にすると結論が反転する**ので、
コードでも列名でもテストでも同じ向きに固定してある）:

- **b** = **対照**が食い違い、候補は食い違わなかった行
- **c** = **候補**が食い違い、対照は食い違わなかった行

**c > b が material の向き。**両方食い違った行と、どちらも食い違わなかった行は、どちらが大きいかに
ついて何も語らないので数えない。

| 判定 | 条件 | 意味 |
|---|---|---|
| `material` | 厳密二項検定が有意で、かつ **c > b** | 入れ替えは「もう一度引く」より大きく動かした。段階Bに金を払う価値がある |
| `indistinguishable` | 有意でない、または食い違いペアが 6 組未満 | **何も示せていない。**「2 冊は同じだ」ではない |
| `control_exceeds_candidate_investigate` | 有意で、かつ **b > c** | ルールブックの話ではない。**自分自身とのほうが食い違う**などということは起きないはずで、道具を見る合図 |

### 構造的な非対称性 — **これは隠さずに書く**

**`live` 腕は 2 つの比較の両方に出てくる。**だから D_cand と D_ctrl は**独立ではない**。
live 腕がたまたま変わった答えを出した行では、両方の食い違いが同時に起きやすくなる。

- **だから 2 つの率を「独立な 2 標本」として比べてはいけない。**区間が重なる／重ならない、という
  読み方をした瞬間に間違いになる
- **対応のある検定は、まさにこの相関を勘定に入れるためのものである。**行ごとに突き合わせるので、
  共有腕による相関は差し引かれる
- 相関の向きも書ける。正の相関は「両方食い違う」「どちらも食い違わない」のマスに確率を寄せるので、
  食い違いペアは**独立を仮定した場合より少なくなる**。必要行数の計算（§4）はその独立仮定で
  やっているので、**必要行数を多めに見積もる**側に外れる。**遅れる向きであって、結論を作る向きではない**

### 20.83% はどうなったか

**捨てていない。出し続けるが、何も決めない。**報告の JSON では
`historical_floor_reference` の中に入り、次の 3 つが必ず添えられる:

- **「順位付き（印あり）の別の描き方で測った数字である」**というラベル
- 実測した床と**有意に違うか**（`measured_floor_differs`）と**どちら向きか**（`measured_floor_direction`）
- 旧設計の区間比較なら何と言ったか（`superseded_screen`）— 検算のために残してある

**実測した床が 20.83% より高ければ、それ自体が発見である。**旧設計は低すぎる床と比べていたことに
なり、`material` が出やすいほうに偏っていたことになる。だから「違った」という事実を payload に書く。

### 段階Aが**言えないこと**

**「候補のほうが良い」とは絶対に言えない。** 全部の答えを悪いほうに変えるルールブックは、
この指標で**満点**を取る。段階Aは「差が大きいか」しか見ておらず、「差の向き（良し悪し）」は見ていない。

これはコードにも書いてある。API の返り値そのものに次の一文が入る:

> `a screening test on whether swapping the rulebook moves the answer MORE than resampling the same rulebook does; it is NOT evidence that either book is better`

## 3. 段階B（Performance / 成績）— 今日は絶対にできないこと

### なぜ過去のスナップショットが使えないのか

**候補ルールブックは、まさにその過去のトレードから作られている。**

実測（2026-09-10）:

- `candidate->>'lessons_considered'` = **60**
- この 60 は postmortem の `RECENT_LESSONS` という**上限値**であって「表の全部」ではない
  （凍結時点で lessons は 75 件、現在 78 件）
- lessons 78 件のうち **60 件**は、`public.analysis_prompts` にプロンプトが保存されている
  分析についてのものである

つまり、**再生に使える過去データと、候補が学習に使ったデータは、ほぼ同じ行**である。

その過去行で候補を採点するのは、答えを見せてから試験を受けさせるのと同じである。候補は必ず良く
見える。良く見えたことは何の証拠にもならない。これを **リーク（leakage）** という。

### だから、こうする

段階Bに使えるのは **凍結時刻より後に生まれたスナップショットだけ**。その行については、候補は
「予測」をしていることになる。

この足切りは **4 か所で強制している**。忘れようがないようにするためで、口約束ではない。

1. **クエリの中**: PostgREST に `created_at=gt.<凍結時刻>` を送っている。あとから TypeScript で
   絞るのではない（あとから絞る実装は、リファクタで消えてもテストが全部通ってしまう）
2. **純関数**: `pairing.ts` の `eligibleForStage` が同じ規則を独立に述べ、クエリと食い違えば
   実行を**拒否**する
3. **データベースのトリガー**: 移行ファイルの `version_compare_runs_respect_the_split`
4. **報告のとき、もう 1 回**: 上の 3 つは全部「実行を**作る**とき」の検査である。実際に数字を
   出すのは報告モードで、そこが採点する行を決めているのは実行ヘッダの `notes.population.ids`
   という列であり、**トリガーはその列を見ていない**（`notes` はリースと封印で書き換わるので、
   意図的に監視対象から外してある）。だから報告モードは、採点しようとしている行の
   `created_at` を**読み直して**、凍結時刻より後であることを確かめてから、初めて結果を読む。
   1 行でも確認できなければ**報告そのものを拒否**する（`stage_b_population_not_forward_only`）

4 番目はレビューで見つかった穴である。それまでは「作るときは 3 重に守られているが、
**数字を出す経路には 1 つも検査がない**」という状態だった。将来だれかが「母集団を広げる」
機能を足したら、トリガーは黙ったまま、テストも全部通ったまま、候補が学習した行の上で McNemar が
回り、その JSON には「候補はこれらの行について何も学んでいない」と書かれていたはずである。

なお報告モードが使う下限は、**実行が宣言した下限と凍結時刻そのものの、遅いほう**である。
移行ファイルをまだ適用していないデータベース（＝トリガーが存在しない状態）でも成立させるため。

なお境界は**「凍結時刻より厳密にあと」**である。同じミリ秒に書かれた行は、記録からは前後関係が
決められない。決められないものは使わない。

### 採点のしかたと、その弱点

腕の答えは「トレードした（traded）」か「見送った（waited）」の 2 つだけ。市場の答えは 2 つの
情報源から取る:

| 情報源 | 条件 | 市場の答え |
|---|---|---|
| `analyses.outcome` | `win` | トレードが正しかった |
| `analyses.outcome` | `loss` | 見送りが正しかった |
| `analyses.wait_check.verdict` | `missed` | トレードが正しかった |
| `analyses.wait_check.verdict` | `correct` | 見送りが正しかった |
| それ以外（`untriggered` / `pending` / `no_call` / `unknown`） | — | **採点できない。行を落とす** |

**ここが設計の一番弱い環である。正直に書く。**

- 腕の答えには**損切りも利確も含まれていない**。「トレードが正しかった」と採点するとき、
  「その腕も本番と同じ水準でトレードしたはずだ」と仮定している。**この仮定は検証していない。**
  損切り幅を広げるようなルールが候補に入っていれば、判断は同じでも結果は変わりうる
- 2 つの情報源は**別のコードが測った別の反実仮想**である。行ごとにどちらで採点したかは記録し、
  報告にも件数を出す
- 実測（2026-09-10）で、プロンプトが保存されている行（同日 15:15 の母集団固定時点で 80 行）のうち
  採点可能なのは win 21 + loss 14 + wait_check の correct/missed 分だけ。**採点できない行はかなり多い**

### 判定のしかた

食い違ったペアだけを数える（両方正解・両方不正解のペアは、どちらが良いかについて何も語らない）。

- **b** = 現行が正解・候補が不正解
- **c** = 現行が不正解・候補が正解

これに**厳密二項検定（McNemar）**をかける。カイ二乗近似は使わない。この harness が数週間で
到達しうる食い違いペア数は 1 桁で、その領域では近似がずれ、しかも**ルールブックを昇格させる
向きにずれる**。

## 4. 何行必要か — **75 は「1 つの比率を定数と比べる」ときの数だった**

事前登録した設計（`docs/NOISE_FLOOR_PREREGISTRATION.md` §4）は Δ=0.20、両側 α=0.05、検出力 80%。
**式は変えていない。変わったのは、その式に何を入れるかである。**

    ψ = 1/2 + (Δ/2)/(Δ + p₀)
    K = z_{α/2}/2 + z_β·√(ψ(1−ψ))
    n = 4K²(Δ + p₀)/Δ²

ここで **p₀ は「効果以外の理由で食い違いペアになる率」**である。**ノイズは検定を偏らせないが、
薄める。**だから必要な行数はノイズ率とともに増える。そして段階が違えば、その率の作り方が違う。

### 段階B: p₀ には**そのまま**食い違い率を入れる（＝ 75 の作り方）

段階Bのペアが「食い違い」になるのは、**2 本の腕が別の判断を出し、かつ市場の答えがその 2 つを
区別したとき**だけ。腕が同じ判断なら、市場が何をしようと両方正解か両方不正解である。だから
食い違いペア率は判断の食い違い率で上から押さえられ、**そのまま入れてよい。** 20.83% を入れると

> ψ = 0.744918、K = 1.346851、n = 74.07 → **対応ペア 75 行**

これは今も正しい計算である。**変わったのはどの率を入れるかだけで、これからは
「この実行の対照腕が測った率」を入れる。** 床が 20.83% のままなら 75 のまま。床がもっと高ければ、
**必要行数はもっと多い**。報告の JSON には**両方**出る（`required_pairs` と
`required_pairs_from_historical_floor`）ので、差がどれだけかは見ればわかる。

### 段階A: p₀ には **2p(1−p)** を入れる（新規。ここが「75 との関係」の答え）

段階Aの観測は**それ自体が「食い違ったか」の 0/1** である。だから「ペアが食い違う」とは
**D_cand と D_ctrl が食い違う**ことで、両方が確率 p のベルヌーイなら（独立なら）その率は
**p ではなく 2p(1−p)** になる。

| 実測した床 p | 段階A の p₀ = 2p(1−p) | 段階A に必要な行数 | 参考: 同じ p での段階B の行数 |
|---|---|---|---|
| 0%（正確計算） | 0% | **39** | 39 |
| 5% | 9.5% | 50 | 38 |
| 10% | 18.0% | 69 | 51 |
| **20.83%（旧・借り物の床）** | **32.99%** | **100** | **75** |
| 25% | 37.5% | 109 | 83 |
| 30% | 42.0% | 118 | 94 |
| 50% | 50.0% | 134 | 134 |

**つまり「75」は段階Bの数字であり、しかも「1 つの比率を定数と比べる」読み方で作られた数字だった。**
段階Aを対応のある 2 比率の比較にすると、**同じ床でも約 100 行**要る。旧設計の段階Aには
そもそも必要行数の計算が無く、corpus 全部を使って区間を重ねていただけである。

**この 100 は多めの見積もりである。**上の 2p(1−p) は D_cand と D_ctrl が独立だとした場合の値で、
実際には `live` 腕を共有しているぶん正の相関があり、食い違いペアは**これより少なくなる**。
相関そのものは**わざとモデル化していない**：それを推定するには、この実行がこれから測ろうとしている
同時分布が要るからで、**これから計算する数に必要行数が依存する設計は、事前登録した設計ではない。**
外れる向きは「必要行数を多めに言う」＝**結論が遅れる向き**であって、結論を作る向きではない。

### 段階Bは何日かかるか

現状の観測ペース（`analysis_prompts` は 2026-09-09 に 48 行、2026-09-10 に 80 行。1 日 15〜30 行）
なら、必要行数が 75〜100 として **おおよそ 3〜7 日**。ただしこれは「毎日同じペースで、すべての行が
採点可能なら」という話であって、上に書いたとおり**採点できない行がかなり出る**ので、実際には
もっとかかる。**この所要日数は見積もりであって測定ではない。**

### 検定ができない場合を、差がない場合と混ぜない

**食い違いペアが 6 組未満だと、どんな結果が出ても統計的には何も言えない**
（両側の厳密二項検定が 0.05 に届く最小が m=6。2×0.5⁶=0.03125）。報告は `underpowered: true` と
書いて出す。「検定して差がなかった」と「検定ができなかった」を同じ顔で出さないためである。
**段階Aの `material` は `underpowered` のときには絶対に出ない。**

### 必要行数がそろって「差なし」と出たとき、それは「候補は良くない」ではない

ここは読み間違えやすいので、はっきり書く。

この設計の Δ=0.20 は**非常に大きな効果**である。ψ = 0.7449 という数字が意味するのは、
**「食い違ったペアの約 74.5% を候補が取る」ほど強い候補**でないと、この行数では検出力 80% に
届かないということである（ψ は床から計算されるので、実測した床が動けばこの値も動く。報告の
`powered_for_discordant_share` に毎回出る）。

したがって:

> **必要行数に到達して `significant: false` が出ても、それは「候補は良くなかった」ではない。
> 「事前登録した幅（食い違いペアの 74.5%）ほどは良くない」というだけである。**
> 本当に少しだけ良い候補は、この設計では必ず「差なし」に見える。

報告の JSON にも `not_significant_means` として同じ一文が入る。

### いつ見るか（optional stopping を塞ぐ）

報告は**無料で何度でも実行できる**。しかも母集団を固定したままでも、時間が経てば結果が確定して
**採点できるペアは増えていく**。ここに規則がないと、3 日目（72 ペア、結論なし）、5 日目
（80 ペア、p=0.09）、8 日目（88 ペア、p=0.04）と見て、**一番良かった日を発表できてしまう**。
これを optional stopping といい、こうすると名目 5% は 5% ではなくなる。

だから規則を 1 つ決めてある:

> **事前登録した必要ペア数に到達した「最初の 1 回」が検定である。**

その 1 回は `version_compare_runs.stage_b_seal` 列に封印される。以後の報告も数字は出すが
`post_hoc_recount: true` が付き、**`conclusive` は封印された 1 回からしか取らない**。
封印列はトリガーで**上書き不可**にしてある（関数側の条件付き UPDATE と DB の二重）。
必要数未満の回は、そもそも `conclusive` になれないので「検定」ではない。
**必要ペア数が実測から決まるようになったが、optional stopping は開いていない。**対照腕の率は
**セル**から計算し、セルは実行が完了した時点で固定され、報告は完了していない実行では数字を出さない。
何度報告しても同じ床・同じ必要数が出る。時間とともに増えるのは採点できるペアの数だけで、それが
封印の対象である。封印には**どの床から必要数を出したか**（`required_pairs_noise_rate`）も一緒に
書き込む。

### 採点の内訳を必ず出す

`b` と `c` は**情報源ごとにも**出す（`by_truth_source`）。理由は、どちらの情報源が付くかが
**現行腕の判断と相関している**からである。`outcome` は本番がトレードした行にしか無く、
`wait_check` は見送った行にしか無い。候補が判断を一方向にずらすと、食い違いペアが片方の情報源に
偏り、p 値が「ルールブックの差」ではなく「その情報源の較正」に乗ってしまう。
まとめた `b`/`c` からは後で分解できないので、最初から分けて出す。

**この内訳は感度チェックであって、追加の検定ではない。** 3 つのうち一番小さい p 値を選んで
発表したら、それは 3 回検定して 1 回だけ報告したということである。事前登録した検定は
**まとめたほうの 1 回だけ**である。

## 5. 検証していないこと（overclaim しないために）

ここは飛ばさずに読んでほしい。**この設計が正しいかどうかは、以下の未検証事項に依存している。**

1. **両方の腕を描き直している（代償は残る。床の未検証は解消した）。** 保存されたプロンプトの
   ルールブロックは「順位付き」で描かれており、各ルールに「今の相場に該当／今は別局面／
   今との照合不可」という**そのときの相場と比べた印**が付いている。候補のルールにはその印を
   作れない（別の過去局面から作られたルールなので、今日計算し直せば「今日の相場」と比べたことに
   なってしまう）。

   そこで **3 本の腕とも、印なしで描き直している**。こうすると腕どうしの違いは「ルールの中身」
   だけになり、対応比較（ペアリング）が成立する。

   **代償（これは残る）: どの腕も、本番が実際に送ったバイト列とは違う。** したがって段階Aが
   測っているのは「印なしの描き方のもとで、ルールを入れ替えると答えが変わるか」であって、
   「本番の答えが変わったはずか」ではない。

   **解消したほう（2026-09-10）:** 前の版はここに「20.83% というノイズ床は印ありの保存バイト列で
   測った数字で、印なしでも同じである保証は**ない。未検証**」と書いてあった。そして
   「印なしの床は**高くなりうる**（取り除いた印は確信を持たせる文言で、いくつかのルールを
   『今は別局面』と固定していたから）。もしそうなら段階Aは低すぎる床と比べ、段階Bの 75 は
   少なすぎ、**どちらもルールブックを昇格させる向きの偏り**」とも書いてあった。

   **その未検証事項を、仮定を足すのではなく測ることで潰した。**対照腕 `live_b` が、同じ行・
   同じ印なしの描き方・同じ日に床を測る。もう「印ありで測った床」と比べていない。

   残る限界: 測った床は**この母集団のこの日の**床である。別の日・別の通貨ペアで同じとは限らない。
   ただしこれは「借り物の定数」とは種類の違う限界で、**実行ごとに測り直される**。

2. **対照腕は「バイト列が同一」の帰無仮説しか押さえていない。**（2026-09-10 のレビューで追加。
   **床の描き方のズレを潰したあと、段階Aに残っている一番鋭い仮定はこれである。**）

   `live_b` は `live` と**まったく同じバイト列**である。一方 `candidate` は**バイト列が違う**。
   したがってこの検定が棄却している帰無仮説は、正確には
   「**候補プロンプトは現行プロンプトと同じ分布から答えを引く**」である。

   問題は、**意味を変えない編集でもこの帰無仮説は破れる**ことである。ルールを 3 つ並べ替える、
   1 つを言い換える——どれもトークン列を動かす。だから `material` が出ても、
   「**新しいルールが分析を変えた**」のか「**プロンプトの字面をいじれば標本が動く**」のかを
   **この設計は区別できない**。実際、候補は 3 ルール → 4 ルールなので、
   「一度も発火しないルールが 1 本増えただけ」でも `material` は出うる。

   **どこまでが被害か。** 段階Aの `material` が買うのは**前向き評価の費用だけ**であって、
   昇格ではない。だから向きは「余計に払う」であって「誤って昇格させる」ではない。
   ただしこの harness が存在する理由は**昇格の向きに間違えないこと**なので、書いておく。

   **直すなら何が要るか。** 4 本目の腕として「**現行のルールを、意味を変えない摂動をかけて**
   描いたもの」が要る。`live_c`（もう 1 本の同一腕）ではない——同一腕をもう 1 本足しても
   床の区間が狭くなるだけで、この区別はつかない。**足していない**（§8）。
   payload では `what_material_does_not_separate` として毎回出る。

3. **3 本の腕は同時ではない。** 1 hop でだいたい 1 セルなので、1 行の 3 セルは数十秒〜数分
   離れた別の瞬間に投げられる。**腕の順番は行ごとに入れ替えている**（`armOrderForRow`、
   6 通りの並びを (run_id, analysis_id) のハッシュで選ぶ）ので、
   「候補との比較はいつも近く、対照との比較はいつも遠い」という系統的なズレは無い
   （2026-09-10 のレビュー指摘。それまでは宣言順に投げていたので、対照の間隔が**常に 2 倍**だった）。
   ただし**間隔そのものが消えるわけではない**: 実行中に配信経路が動けば、その分は
   D_cand と D_ctrl の**両方**に乗る。乗り方が偏らなくなっただけである。

4. **web 検索を外している。** 両腕とも `tools` なし。#64 の主アームと同じで、比較は「再生 対 再生」
   なので内部妥当性は保たれるが、**本番の経路（検索あり）でも同じ数字になる保証はない**。

5. **段階Bの採点仮定**（§3 の「一番弱い環」）。腕の答えに水準（損切り・利確）が含まれていないこと。
   **未検証**。対照腕はここには効かない。対照腕が測るのは**同じ本の再現性**であって、
   「腕の判断と本番の建玉が同じ運命をたどったか」ではない。**この設計の一番弱い環は今も弱い。**

6. **母集団が狭い。** 実測で通貨ペアは 1 種（USD/JPY）、アカウントは少数、期間は数日。
   読める主張は「これらのスナップショットについて」だけである。

7. **対照腕は「1 回の再サンプル」でしかない。** `live_b` は live を**もう 1 回**引いただけなので、
   床の推定は 1 行あたり 1 回の反復に基づく。#64 は同じ行を N=2 で引いて 48 行の床を出した。
   ここも 1 行 1 反復なので、床の**点推定**は不偏だが、区間は行数ぶんの幅しか縮まらない。
   4 本目の腕（live_c）を足せば精度は上がるが、費用は 1 行 4 セルになる。**足していない。**

8. **`live` 腕が 2 つの比較に共有されている**（§2 の「構造的な非対称性」）。対応のある検定は
   それを勘定に入れるが、必要行数の計算では**独立を仮定している**。外れる向きは
   「必要行数を多めに言う」＝結論が遅れる向きである（§4）。

9. **`lessons_considered = 60` は「表の全部」ではない。** これは設計の前提として渡されていたが、
   本番を数え直すと 60 は上限値で、凍結時点の lessons は 75 件だった。リークの結論は変わらない
   （60 件のうち大半が再生対象の分析についてのものだから）が、**理由が違うので直した**。

## 6. お金の話

このハーネスは**呼ぶたびに課金される**。しかも本番アプリの分析と postmortem と**同じ API キー**
を使う。2026-09-08 には、そのキーの残高切れで実利用者の画面にエラーが出ている。

### 腕が 3 本になったぶん、費用は約 1.5 倍

**これは今回の変更で増えた分であり、オーナーが承知のうえで払うと決めた分である。**

実測（中止した試算実行 e6a97341… の 28 セルから再計算）:

- 1 セルあたりの入力トークン **平均 8,819**、**最大 9,511**
- 母集団は 2026-09-10 時点で **80 行**

したがって 3 本腕なら:

| | 2 本腕（旧） | 3 本腕（今） |
|---|---|---|
| セル数 | 160 | **240** |
| 入力トークン（実測平均から） | 約 141 万 | **約 212 万** |
| 出力トークンの**上限**（8,000 × セル数） | 128 万 | **192 万** |

出力側は**上限であって実測ではない**。`count_tokens` は入力しか数えず、出力はモデルが書いた分だけ
`max_tokens` まで課金される。**見積もりを実測として書かない。**

なお `live` と `live_b` はバイト列が同じだが、**試算でも 2 回数える**。1 回数えて 2 倍すれば
足りるが、それは「実際には値段を確かめていないリクエスト」の予算を出すことになる。無料の
`count_tokens` を 1 回余分に使って、試算のセルと実行のセルを 1 対 1 で対応させている。

だから制御は「警告」ではなく「拒否」にしてある。すべて noise-floor からそのまま持ってきた:

- `dry_run` は**既定で true**。フィールドを書き忘れても、綴りを間違えても、そもそも JSON でなくても
  無料の経路に落ちる。**明示的な `false` だけ**が課金経路に届く
- 課金する実行は、**完了した dry run なしには作れない**。予算 2 本は dry run が実測した数字から
  選び、その 2 倍を超える予算は**拒否**される（psql のヒアドキュメントでゼロを 1 個多く打つと
  桁が 1 つ増えるので）
- 1 回の呼び出しで扱えるセル数はサーバ側で上限 4
- 支出は「呼び出し回数」ではなく毎回の `usage` から**実測**する。加えて、**測れなかった支出は
  ゼロとして扱わない**（タイムアウトした呼び出しは請求されるのに usage が返らない）
- 呼び出しは**厳密に直列**、しかも**前の呼び出しが終わってから 20 秒**空ける。これは
  「以前のハーネスがエッジワーカーを 40 分占有し、実利用者の分析が 1 件つながらなかった」
  という実測から来た数字である
- pg_cron が動く 9 つの分（3, 8, 13, 18, 23, 33, 38, 48, 53）には**セルを開始しない**し、
  **その分にまたがって走りもしない**
- 1 つの dry run が認可できる課金実行は 1 つだけ（関数側の検査と、DB の部分ユニーク索引の二重）
- 401 / 403 / 429 と残高エラーは**リトライしない。実行ごと止める**

**pg_cron に登録してはいけない。**このジョブは存在しないし、作ってもいけない。操作者が SQL から
手で叩く。トークンは vault から SQL の中で読み、値はどこにも書き残さない。

## 7. 実行手順（要約）

すべて `x-sweep-token` ヘッダ付きの POST。**この順番以外では課金経路に到達できない。**

**0. 先に移行ファイル `20260910200000_measure_the_floor_with_the_same_ruler.sql` を適用すること。**
これを当てるまで `arm` の CHECK 制約が `('live','candidate')` のままなので、`live_b` のセルは
insert できない。試算はセルを書かないので、**適用しなくても手順 2 までは通ってしまう**。

**「落ちるだけで無料」ではない。**（2026-09-10 のレビューで前の版の記述が間違っていた。）
セルは行ごとに 3 腕まとめて積まれ、1 hop でだいたい 1 セルしか買えないので、実際に起きるのは
こうなる: 最初の行の `live` と `candidate` が**普通に買われ**（＝**課金が 2 回発生する**）、
3 セル目の `live_b` で claim が CHECK 違反になる。つまり **claim が課金の前にあることは、
その行のその腕を守るだけで、すでに買った 2 セルは戻らない**。

さらに、**その失敗は次の hop でも同じように起きる**。この「進捗ゼロで止まった hop は
chain を渡さない」という歯止めは今回入れた（`hard_stop`）。入れる前は
`max_chain_hops` ぶん（3 腕・80 行なら **285 回**）空回りの edge 呼び出しが連続していた。
今は最初の失敗で chain が止まり、応答は **HTTP 500 / `ok:false` / `hard_stop` 付き**で返る。
前は **HTTP 200 / `ok:true` / `errors` の中に 1 行**だったので、見落とせた。

1. **凍結**（無料）: `{"action":"freeze"}` → `freeze_id` が返る
2. **試算**（無料）: `{"freeze_id":"…","stage":"materiality"}` → 入力トークンの実測値と
   出力トークンの上限が返る。`dry_run` は書かなくてよい（既定で true）
3. **実行**（課金）: `{"dry_run":false,"dry_run_id":"…","stage":"materiality",
   "budget_input_tokens":N,"budget_output_tokens":M,"chain":true}`
   — N と M は 2 で見た数字から選ぶ
4. **続き**: `{"dry_run":false,"run_id":"…","chain":true}`
5. **止める**: `version_compare_runs` の `status` を `paused` に UPDATE する。次の hop が読んで止まる
6. **報告**（無料）: `{"report_run_id":"…"}` — 全セル（**行数 × 3**）が揃うまで**数字を出さない**

**中止した実行は再開も報告もできない。**`status='aborted'` の実行に `run_id` を渡すと拒否され、
`report_run_id` に渡しても拒否される。DB のトリガーも `aborted` から他の状態への UPDATE を拒否する。
実際、2 本腕の設計で作られた e6a97341-69a4-443f-b877-5eed16d4ec34 は
`abort_reason='superseded_by_control_arm_design'` で止めてある。**新しい試算を取り直すこと。**

段階Bは 1 と 2 のあいだに時間を空ける。凍結直後に `stage:"performance"` で試算すると、
**「凍結以降に書かれたスナップショットが 1 件もない」と拒否される。**それが正しい動作である。

### 手間の実測見積もり（始める前に知っておくこと）

**手順 2（試算）は思ったより回数が要る。** 現在の 80 行 × **3 腕** = **240 回**の `count_tokens`
（無料）が必要で、これも 20 秒間隔・1 回の呼び出しあたり 6 件程度なので、
**手動 POST が 40 回**くらいになる。しかも**試算は自動で次の hop を呼ばない**（`chain` なし）。
noise-floor が 8 回程度で済んだのは、あちらの 2 本の腕がバイト単位で同一で、行ごとに 1 回だけ
数えれば足りたからである。こちらは 3 本のうち 1 本の中身が違い、かつ同一の 2 本も別々に
数えているので、行ごとに 3 回数える。

もう 1 つ。プロンプトが `technical_fallback` の行が 1 つでも混じると、試算は永久に
`complete: false` のままになり、**課金実行を作れなくなる**。2026-09-10 時点の内訳は
full が大半 / technical_only 数件 / technical_fallback **0** なので今は起きないが、これは
「今のデータがそうだ」というだけで保証ではない。**止まる向きに壊れる**設計ではあるが、
起きたときはバグに見えるので、先に書いておく。

## 9. 数式（読まなくてよい）

事前登録（`docs/NOISE_FLOOR_PREREGISTRATION.md` §4）のものをそのまま使っている。

    ψ = 1/2 + (Δ/2)/(Δ + p₀)
    K = z_{α/2}/2 + z_β·√(ψ(1−ψ))
    n = 4K²(Δ + p₀)/Δ²

Δ = 0.20、z_{α/2} = 1.959964、z_β = 0.841621。p₀ = 0 ではこの式が壊れる（ψ が 1 になって
√ の項が消え、n が 20 まで落ちる）ので、そこだけは正確計算の **39** を使う。実装は
`mcnemar.ts` の `requiredPairs` で、`src/test/version-compare.test.ts` が上の表を 1 行ずつ
突き合わせている。どちらかが動けばテストが落ちる。b と c の向きも同じテストで固定してあり、
**入れ替えたら `material` ではなく `control_exceeds_candidate_investigate` が出る**ことまで
確かめている。

**p₀ に何を入れるかは段階で違う**（§4）。段階Bは食い違い率をそのまま。段階Aは観測自体が
0/1 の「食い違ったか」なので、独立を仮定した食い違いペア率

    p₀ = 2p(1−p)

を入れる（p は実測した対照腕の食い違い率）。実装は `mcnemar.ts` の `nullDiscordantRate`。

McNemar の厳密二項検定は m = b + c として

    p = min(1, 2 · P(X ≤ min(b,c)))    ただし X ~ Bin(m, 1/2)

段階Aでの b と c の向きは（**逆にすると結論が反転するので**）

    b = 対照だけが食い違った行の数
    c = 候補だけが食い違った行の数     c > b が material

二項係数は 1 度も作らない（`C(200,100)` は約 9×10⁵⁸ で、先に作ると桁が落ちる）。
0.5^m から確率質量を掛け算で進める。
