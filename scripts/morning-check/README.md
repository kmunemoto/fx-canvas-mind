## 2. How to use it (every morning)

1. **Choose the day.** `X` = today's date in UTC. The GMO day key is `K = X - 1 day` as `YYYYMMDD`. The range is one GMO day, 21:00 UTC to 21:00 UTC:
   `START_MS` = epoch milliseconds of `(X - 2 days) 21:00:00 UTC`, `END_MS = START_MS + 86400000`. A bar belongs to the day when `START_MS <= its OPEN time < END_MS`.
   - Bash: `python3 -I -c "import datetime as d; x=d.datetime.now(d.timezone.utc).date(); s=int(d.datetime(x.year,x.month,x.day,21,tzinfo=d.timezone.utc).timestamp()*1000)-2*86400000; print(s, s+86400000, (x-d.timedelta(days=1)).strftime('%Y%m%d'))"`
   - or SQL (a separate cheap SELECT): `select (extract(epoch from (date_trunc('day', now() at time zone 'utc') - interval '2 days' + interval '21 hours') at time zone 'utc') * 1000)::bigint as start_ms`
   - Both agreed on 2026-10-13: `START_MS 1791752400000, END_MS 1791838800000, K 20261012`. The run of **2026-10-14 00:16 UTC** is `START_MS 1791838800000, END_MS 1791925200000, K 20261013`.
   - Tuesday run = Monday key (23 bars per pair, the first bar opens Sunday 22:00 UTC); Wednesday to Friday runs = 24 bars; Saturday run = Friday key (see limits: the file is not stored yet); the Tuesday run also counts the previous Friday key (X minus 4 days).
   - Give the START_MS and END_MS in MILLISECONDS. In seconds the answer is `NO_DATA` with `range_utc` in 1970 (tested); shifted by an hour it is `BAD_RANGE` (tested).
2. **Pairs:** take `pairs.min.sql`, replace `{{START_MS}}` and `{{END_MS}}` by the two numbers (plain text substitution), send it as `query` to `execute_sql`. **Gold:** the same with `gold.min.sql`. Two calls; inside the database a day takes about 0.6 s (pairs) and 0.15 s (gold) (section 7). An answer is about 7 to 9 KB for a pairs day and 1.5 to 3 KB for gold (counted from the returned texts; the tool printed them inline).
3. **Read the answer in this order:** the `RUN` row (right range? how long?), the `SUMMARY` rows (one per instrument: verdict `OK` or what is wrong), then the `LINE` rows (one per expected fire and per mail).
4. Report only what the rows say. A day with no expected fire and no mail is a normal `OK` day, not a failure. `OK` can coexist with `not_mailable` lines (section 4). Do not call a `near_edge` line a defect without saying so (section 5). `CHECK`, `NO_DATA`, `STALE_ROW` and `BAD_RANGE` are the words that need a human look.
5. For the author of the Routine prompt: the two statements are plain text of 22.2k and 19.2k characters (one `execute_sql` call each accepted them, many times), so they can be kept in the repository and read at run time, or pasted into the prompt. They must not be edited by the Routine. The prompt should name the verdict meanings of section 4 and the limits of section 8 (especially: Saturday-morning pairs = `NO_DATA` is expected; if the 2026-10-14 answer is `NO_DATA` the report must say "not checked", not "all fine"; gold is the latest row; win rate and profit or loss are not measured). The sweep log `net._http_response` is NOT used by these statements; it keeps only about 6 hours, so at 00:16 UTC it could support only the last two or three bars of the day (open 18:00, 19:00, 20:00) and the prompt should not promise a whole-day comparison with it.

## 3. Output contract (the same columns for pairs and gold)

## 4. Verdict meanings and suggested wording for the Japanese report

| verdict | what it means | suggested wording (owner report) |
|---|---|---|
| `ok` | the recount expects this fire, a mail group exists, every row has status `sent`, rows <= max(subscriptions, 1) | 「数え直しの合図とメールが一致（◯通・送信済み・遅れ◯秒）」 |
| `missing` | the recount expects the fire, production COULD have mailed it (no reason in `why`), but there is no row | 「数え直しでは合図なのにメールの行が無い（要調査）」 |
| `extra` | a mail group exists but the recount has no fire there. `why`: `recount has the OPPOSITE cross (SELL)`, `recount has this cross but macd does not reach the level`, or `recount has no cross at this bar (side stays UP/DOWN)` | 「メールはあるが、数え直しではその足に合図が無い」 |
| `not_mailable` | the recount expects the fire, but production cannot mail it; `why` gives the reason(s) separated by `;` (below) | 「数え直しでは合図だが、本番は仕組み上メールを出せない（理由）」 |
| `not_sent` | expected fire, rows exist, but at least one row's status is not `sent` (see `mail_status`) | 「メールの行はあるが送信済みでない」 |

SUMMARY wording: `NO_DATA` 「その日のデータが無く、数え直していない（確認できていない）」, `CHECK` 「数え直したが要確認の点がある（attention の内容）」, `entry_differs` 「メールの約定目安と数え直しの終値が◯ティックずれている（最後の終値の改定の可能性。near_edge も見る）」.

`not_mailable` reasons: `weekend_window` (the bar's CLOSE time is in Friday >= 21:00, Saturday or Sunday < 22:00 UTC, which the sweep never judges; the last summer bar of the week, opened Friday 20:00, is an example), `before_go_live` (the bar opened before the rule was live: pairs before 2026-10-12 16:00 UTC, gold before 2026-10-13 05:00 UTC), `no_subscription` (the pair has no row in `signal_alert_subscriptions` for interval 1h, rule macdx now), `twelve_daily_cap` (gold only: `public.twelve_data_usage.used >= 780` on the UTC day the bar closed; the sweep stops reading Twelve Data there).

A `missing` line is a question, not a verdict. First look at `near_edge`, then ask whether the sweep read that hour (`net._http_response` keeps only about 6 hours; its JSON answer also counts `not_allowed`), then the cap and subscriptions. A SUMMARY `NO_DATA` on a Saturday-morning run is expected for the pairs and is no alarm.

Statuses production writes for these mails (`signal-alerts/index.ts` `deliver`): `pending` (row claimed, mail not finished: a crash or a send in flight), `sent`, `failed` (the `error` column holds the provider's text or `no_email`; it is NOT read here, it may contain an address) and `not_configured` (no mail key set). On 2026-10-13 10:59 UTC the table held 498 rows (496 `signal`, 2 `test`), all `sent` (my own count by kind and status): so `not_sent` has never happened on real data and is tested only with the fake mails of section 7.

One reason for a legitimately absent row is invisible to the SQL: production writes NO row for a subscriber who is not allowed (`alertsAllowed` in `signal-alerts/logic.ts`: a paid plan light / standard / pro, or an e-mail on the admin allowlist); it only counts `not_allowed` in its JSON answer. On 2026-10-13 each of the 6 subscribed instruments has exactly 1 subscription and 0 of them has a paid plan (counts only, round 1), so the current mails depend on the e-mail allowlist, which cannot be evaluated without reading e-mail addresses (not done).

## 5. Reading the numbers: `near_edge`, ticks and the mail's `entry`

Production judged each pair bar on the live file 2 to 6 s after the close; the table holds the final file, and gold is the latest stored row. If the last close of a bar was revised, a decision can flip. `cross_edge_ticks` = how many ticks (1 tick = 10^-d, d = 3 for ...JPY, 5 for the other pairs, 2 for gold) the bar's own last close would have to move to turn the sign of `h = macd - signal`; `level_edge_ticks` = the same for macd crossing the level. `near_edge` is true when either is **2 ticks or less**. The slopes are exact consequences of the rule: `d(h)/d(last close) = (2/13 - 2/27) x (1 - 2/10) = 0.0638`, and `d(macd - level)/d(last close) <= (2/13 - 2/27) + 0.8/599 = 0.0811` (the verifier measured numerical slopes 0.06382 and 0.07844 to 0.08111). The 2-tick tolerance comes from the inventory's comparison of production `entry` values with the table (`inv/pairs-spec.md` 2.4): 2 of 61 differed, each by +1 tick, JPY pairs, 15-minute bars; on 1-hour bars 0 of 3 differed, which is too few to say anything. So the tolerance is **not measured for 1-hour bars** (and not at all for gold).

`entry` is the rounded close of the judged bar as production saw it (live file, 2 to 6 s after the close). `close` is the same bar in the final stored file. `entry_diff_ticks <> 0` therefore means either that the last close was revised between the live read and the final file, or that the recount and production read different data: it is not proof of an error, but `attention` shows `entry_differs=n` and the verdict is `CHECK` so that a human looks (read `near_edge` of that line first). The only real mail checked so far (USD/JPY SELL 2026-10-12 20:00) has `entry` 158.612 = `close`, `entry_diff_ticks 0`.

Examples from the tests: USD/JPY 2026-09-27 22:00 BUY had `cross_edge_ticks 0.7` (a knife-edge fire that a one-tick revision removes; verifier).

## 6. What the SQL does (the recount, in the app's own terms)

Rule (`_shared/macd.ts`, `pine.ts`, `macd-level.ts`, `macd-extreme.ts`, `signal-alerts/indicators.ts`): for every CLOSED 1-hour bar, on the 600 closed series entries ending at it (entries, not hours): MACD(12,26,9) as Pine computes it (SMA seed, then `alpha*v + (1-alpha)*prev`, the same order of double operations as the TypeScript); `h = macd - signal`; side = sign(h), `h = 0` keeps the previous side; a **cross** = the side changed; usual move = mean of `|close step|` over the 599 steps (added in order); `level = 0.8 x usual move` (not rounded). **SELL** when the cross is DOWN and `macd >= level`; **BUY** when the cross is UP and `macd <= -level`; equality fires; no rounding in the comparison.

Data path of the five pairs (`front-pairs.part`), now exactly the order production keeps: the 1-hour BID and ASK day files of the 40 days up to key K (`public.gmo_kline_files`) -> rows whose `openTime/open/high/low/close` are plain numbers (`parseKlines`; a file's rows are read sorted by open time, equal times keeping their file order) -> `mergeSides`: the ASK of an open time is the LAST ASK row in arrival order (files in ascending key order); the BID rows are walked in arrival order and the FIRST one that has an ASK and is not above it (`ask < bid` skips the row without emitting it) is the bar; no ASK -> dropped; nothing is dropped for a zero close; the list keeps this arrival order and is never sorted again (`seq`) -> `mid = (bid + ask) / 2` as a double -> drop bars the market was shut for the whole of (open and open + 1 h - 1 ms both in Friday >= 22:00, Saturday, Sunday < 21:00 UTC) -> round like JS `Number(m.toFixed(d))` (d = 3 for JPY pairs, else 5) -> rank 1..n in that order. Gold (`front-gold.part`): the ONE row of `public.live_chart_fallback` (XAU/USD, 1h), only bars whose end is not after the moment the row was read, in the row's order (the stored bars already passed `parseCandles`: price > 0, coherent, sorted, one bar per time), rounded like `Number(c.toFixed(2))`.

The rounding is emulated exactly: the double's 52-bit mantissa gives `m = mant / 2^(52-k)`, and the result is `round_half_up(mant x 10^d / 2^(52-k)) / 10^d`, which is what `toFixed` does on the exact binary value (half-way cases included). `bad_mantissas` counts closes whose mantissa is outside [2^52, 2^53) (a zero or absurd mid); it must be 0.

Each judged bar gets its own recursion over its 600 closes (the shipped SQL does not use one long recursion over the whole history; both were shown to give identical bits, section 7). Mails: `public.signal_alerts` with `kind = 'signal'`, `interval = '1h'`, the exact rule id, `bar_time` (= the bar's OPEN) in the range, grouped per (pair, side, bar). Subscriptions are only counted (`signal_alert_subscriptions`, interval 1h, rule macdx; no `user_id`).

Performance notes for whoever edits `src/`: do not join the series inside the recursion (the planner chose nested loops and a 35 s run); keep the decimals `d` in `syms`; keep `fin` `materialized`; look closes up by rank in the per-symbol array (`closes`).

## 11. debug-closes (for a Deno or Python replay)

Replace `{{START_MS}}` / `{{END_MS}}` as above, and `{{SYMBOL}}` (`USD_JPY`, `EUR_JPY`, `AUD_JPY`, `EUR_USD`, `AUD_USD` or `*`) and `{{CHUNK}}` in `debug-closes.min.sql`; `{{CHUNK}}` only in `debug-closes-gold.min.sql`. `CHUNK = -1` returns the list of pieces with their md5 and no strings; `0, 1, 2 ...` returns one piece (about 250 bars) as `open_ms:close;open_ms:close;...` with the close written with its decimals (`158.612`, `1.11711`, `4137.60`). Take the pieces of a symbol in order and join them with `;`. The series runs from 599 bars before the day's first judged bar to the day's last bar, which is what the recount used. For gold the column `row_read_utc` says which version of the stored row was used.

## 12. Rebuild

`bash src/build.sh` (needs `python3`) rewrites the eight deliverables from the parts: head, front (pairs or gold), engine, back1, guard (pairs or gold), back2, and for the debug files the tail. `src/assemble.py` concatenates parts, replaces `{{NAME}}` given with `--sub NAME=VALUE`, and with `--strip` removes full-line comments, blank lines and leading blanks. Every comment in a part is a full line starting with `--`. Run the structural checks of section 1 again after a rebuild (markers once each, ASCII, no `;`).
