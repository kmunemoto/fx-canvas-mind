### v5.5 `near_edge`

The same question as v4 (would moving the bar's own final close change the decision at that bar), evaluated in closed form from the state one row earlier in the same way, but the v5 decision is **not monotone** in the last close: a SELL needs the close low enough for `h` to turn below zero (the cross) and high enough for `m` to stay at or above the mark, so it holds on a band of closes. The statement therefore tries all four closes -2, -1, +1 and +2 ticks away (the closes lie on that tick grid) instead of v4's two end points. The side at the bar before (`side_p`) does not depend on the last close; at the moved close a bar `h` of exactly 0 keeps `side_p` (no cross).

### v4.5 `near_edge` (exact) and the gold Saturday fix

`near_edge` keeps its meaning and is now exact instead of a slope estimate: **moving the bar's own final close by 2 ticks (up or down) would change the entry decision at that bar** (SELL / BUY / none). Production read the live file 2 to 6 s after the close and the table holds the final one, so a revised last close could add or remove an entry. Only the last step of the recursion depends on that close, so the statement evaluates that step again from the state one row earlier (`e12_p`, `e26_p`, `sg_p`, the edge extremes of positions 480 .. 598) for the close moved by -2 and +2 ticks (the moved close is the rounded price 2 ticks away: exact decimal arithmetic, then the nearest double, like every rounded close), with the same double operations as the recursion, and compares the decision with the unmoved one. Bar i-1 does not depend on the last close. The decision is monotone in the last close (the top-band test can only turn true as the close rises, the bottom-band test only as it falls; the two cannot hold together; every term of T, `m - 0.9 s`, `m - 0.9 h` and `m - 0.9 T(i-1)` grows with the close), so the two end points tell whether any move inside +-2 ticks changes it. `near_edge` is on every `LINE` that has a window (entries and mails alike); read it first on a `missing` or `extra` line.

**Gold, Saturday morning (finding F1, fixed in v4 only).** The sweep stops at the weekend window, so on a Saturday the stored gold row ends with the Friday 19:00 bar: the 20:00 bar closes at Friday 21:00 (weekend window), is never judged, and is not in the row. v3 compared the day's last bar with `END_MS - 1 h` and answered `CHECK last_day_bar_not_at_day_end` for such a day. v4 compares it with the last judgeable bar of the range (`last_judgeable_open_utc`): `OK` when the row reaches it (a row read later that does hold the 20:00 bar is fine too). A Saturday KEY (K the Saturday, range Friday 21:00 to Saturday 21:00) is `NO_DATA` as before, without the false attention text.

**`twelve_daily_cap` looks at the day's last usage count only (finding S4, kept as it is).** `extra_reasons` joins `public.twelve_data_usage` on the UTC date the bar closed and tests `used >= 780` of that row, which is the day's count at its last update (the table holds one row per day: `day`, `used`, `updated_at`). The sweep stops reading Twelve Data when the count reaches 780, so a fire BEFORE that moment could have been mailed, but the statement marks every fire of that UTC day `not_mailable` with `twelve_daily_cap`. A `not_mailable` line with this reason hides a possible miss on a day with a high count: read the bar's time against the day's count (`used` was at most 170 in the 12 days up to 2026-10-14, so the cap has not been near in practice). Not changed.

## 2. How to use it (every morning)

1. **Choose the day.** `X` = today's date in UTC. The GMO day key is `K = X - 1 day` as `YYYYMMDD`. The range is one GMO day, 21:00 UTC to 21:00 UTC:
   `START_MS` = epoch milliseconds of `(X - 2 days) 21:00:00 UTC`, `END_MS = START_MS + 86400000`. A bar belongs to the day when `START_MS <= its OPEN time < END_MS`.
   - Bash: `python3 -I -c "import datetime as d; x=d.datetime.now(d.timezone.utc).date(); s=int(d.datetime(x.year,x.month,x.day,21,tzinfo=d.timezone.utc).timestamp()*1000)-2*86400000; print(s, s+86400000, (x-d.timedelta(days=1)).strftime('%Y%m%d'))"`
   - or SQL (a separate cheap SELECT): `select (extract(epoch from (date_trunc('day', now() at time zone 'utc') - interval '2 days' + interval '21 hours') at time zone 'utc') * 1000)::bigint as start_ms`
   - Both agreed on 2026-10-13: `START_MS 1791752400000, END_MS 1791838800000, K 20261012`. The run of **2026-10-14 00:16 UTC** is `START_MS 1791838800000, END_MS 1791925200000, K 20261013`.
   - Tuesday run = Monday key (23 bars per pair, the first bar opens Sunday 22:00 UTC); Wednesday to Friday runs = 24 bars; Saturday run = Friday key (see limits: the file is not stored yet); the Tuesday run also counts the previous Friday key (X minus 4 days).

## 4. Verdict meanings and suggested wording for the Japanese report

| verdict | what it means | suggested wording (owner report) |
|---|---|---|
| `ok` | the recount expects this fire, a mail group exists, every row has status `sent`, rows <= max(subscriptions, 1) | 「数え直しの合図とメールが一致（◯通・送信済み・遅れ◯秒）」 |
| `missing` | the recount expects the fire, production COULD have mailed it (no reason in `why`), but there is no row | 「数え直しでは合図なのにメールの行が無い（要調査）」 |
| `extra` | a mail group exists but the recount has no fire there. `why`: `recount has the OPPOSITE cross (SELL)`, `recount has this cross but macd does not reach the level`, or `recount has no cross at this bar (side stays UP/DOWN)` | 「メールはあるが、数え直しではその足に合図が無い」 |
| `not_mailable` | the recount expects the fire, but production cannot mail it; `why` gives the reason(s) separated by `;` (below) | 「数え直しでは合図だが、本番は仕組み上メールを出せない（理由）」 |
| `not_sent` | expected fire, rows exist, but at least one row's status is not `sent` (see `mail_status`) | 「メールの行はあるが送信済みでない」 |
| `dup` | expected fire, all rows sent, but more rows than the pair has subscriptions now | 「購読数より行が多い」 |
| `unchecked` | a mail exists but the recount has no window for that bar (the key's files are not in the table yet, or fewer than 600 bars before it), so nothing can be said | 「数え直せなかった（データ未保存）」 |

SUMMARY wording: `NO_DATA` 「その日のデータが無く、数え直していない（確認できていない）」, `CHECK` 「数え直したが要確認の点がある（attention の内容）」, `entry_differs` 「メールの約定目安と数え直しの終値が◯ティックずれている（最後の終値の改定の可能性。near_edge も見る）」.

`not_mailable` reasons: `weekend_window` (the bar's CLOSE time is in Friday >= 21:00, Saturday or Sunday < 22:00 UTC, which the sweep never judges; the last summer bar of the week, opened Friday 20:00, is an example), `before_go_live` (the bar opened before the rule was live: pairs before 2026-10-12 16:00 UTC, gold before 2026-10-13 05:00 UTC), `no_subscription` (the pair has no row in `signal_alert_subscriptions` for interval 1h, rule macdx now), `twelve_daily_cap` (gold only: `public.twelve_data_usage.used >= 780` on the UTC day the bar closed; the sweep stops reading Twelve Data there).

A `missing` line is a question, not a verdict. First look at `near_edge`, then ask whether the sweep read that hour (`net._http_response` keeps only about 6 hours; its JSON answer also counts `not_allowed`), then the cap and subscriptions. A SUMMARY `NO_DATA` on a Saturday-morning run is expected for the pairs and is no alarm.

Statuses production writes for these mails (`signal-alerts/index.ts` `deliver`): `pending` (row claimed, mail not finished: a crash or a send in flight), `sent`, `failed` (the `error` column holds the provider's text or `no_email`; it is NOT read here, it may contain an address) and `not_configured` (no mail key set). On 2026-10-13 10:59 UTC the table held 498 rows (496 `signal`, 2 `test`), all `sent` (my own count by kind and status): so `not_sent` has never happened on real data and is tested only with the fake mails of section 7.

One reason for a legitimately absent row is invisible to the SQL: production writes NO row for a subscriber who is not allowed (`alertsAllowed` in `signal-alerts/logic.ts`: a paid plan light / standard / pro, or an e-mail on the admin allowlist); it only counts `not_allowed` in its JSON answer. On 2026-10-13 each of the 6 subscribed instruments has exactly 1 subscription and 0 of them has a paid plan (counts only, round 1), so the current mails depend on the e-mail allowlist, which cannot be evaluated without reading e-mail addresses (not done).

## 5. Reading the numbers: `near_edge`, ticks and the mail's `entry`

Production judged each pair bar on the live file 2 to 6 s after the close; the table holds the final file, and gold is the latest stored row. If the last close of a bar was revised, a decision can flip. `cross_edge_ticks` = how many ticks (1 tick = 10^-d, d = 3 for ...JPY, 5 for the other pairs, 2 for gold) the bar's own last close would have to move to turn the sign of `h = macd - signal`; `level_edge_ticks` = the same for macd crossing the level. `near_edge` is true when either is **2 ticks or less**. The slopes are exact consequences of the rule: `d(h)/d(last close) = (2/13 - 2/27) x (1 - 2/10) = 0.0638`, and `d(macd - level)/d(last close) <= (2/13 - 2/27) + 0.8/599 = 0.0811` (the verifier measured numerical slopes 0.06382 and 0.07844 to 0.08111). The 2-tick tolerance comes from the inventory's comparison of production `entry` values with the table (`inv/pairs-spec.md` 2.4): 2 of 61 differed, each by +1 tick, JPY pairs, 15-minute bars; on 1-hour bars 0 of 3 differed, which is too few to say anything. So the tolerance is **not measured for 1-hour bars** (and not at all for gold).

`entry` is the rounded close of the judged bar as production saw it (live file, 2 to 6 s after the close). `close` is the same bar in the final stored file. `entry_diff_ticks <> 0` therefore means either that the last close was revised between the live read and the final file, or that the recount and production read different data: it is not proof of an error, but `attention` shows `entry_differs=n` and the verdict is `CHECK` so that a human looks (read `near_edge` of that line first). The only real mail checked so far (USD/JPY SELL 2026-10-12 20:00) has `entry` 158.612 = `close`, `entry_diff_ticks 0`.

Examples from the tests: USD/JPY 2026-09-27 22:00 BUY had `cross_edge_ticks 0.7` (a knife-edge fire that a one-tick revision removes; verifier).

## 6. What the SQL does (the recount, in the app's own terms)

Rule (`_shared/macd.ts`, `pine.ts`, `macd-level.ts`, `macd-extreme.ts`, `signal-alerts/indicators.ts`): for every CLOSED 1-hour bar, on the 600 closed series entries ending at it (entries, not hours): MACD(12,26,9) as Pine computes it (SMA seed, then `alpha*v + (1-alpha)*prev`, the same order of double operations as the TypeScript); `h = macd - signal`; side = sign(h), `h = 0` keeps the previous side; a **cross** = the side changed; usual move = mean of `|close step|` over the 599 steps (added in order); `level = 0.8 x usual move` (not rounded). **SELL** when the cross is DOWN and `macd >= level`; **BUY** when the cross is UP and `macd <= -level`; equality fires; no rounding in the comparison.

Data path of the five pairs (`front-pairs.part`), now exactly the order production keeps: the 1-hour BID and ASK day files of the 40 days up to key K (`public.gmo_kline_files`) -> rows whose `openTime/open/high/low/close` are plain numbers (`parseKlines`; a file's rows are read sorted by open time, equal times keeping their file order) -> `mergeSides`: the ASK of an open time is the LAST ASK row in arrival order (files in ascending key order); the BID rows are walked in arrival order and the FIRST one that has an ASK and is not above it (`ask < bid` skips the row without emitting it) is the bar; no ASK -> dropped; nothing is dropped for a zero close; the list keeps this arrival order and is never sorted again (`seq`) -> `mid = (bid + ask) / 2` as a double -> drop bars the market was shut for the whole of (open and open + 1 h - 1 ms both in Friday >= 22:00, Saturday, Sunday < 21:00 UTC) -> round like JS `Number(m.toFixed(d))` (d = 3 for JPY pairs, else 5) -> rank 1..n in that order. Gold (`front-gold.part`): the ONE row of `public.live_chart_fallback` (XAU/USD, 1h), only bars whose end is not after the moment the row was read, in the row's order (the stored bars already passed `parseCandles`: price > 0, coherent, sorted, one bar per time), rounded like `Number(c.toFixed(2))`.

The rounding is emulated exactly: the double's 52-bit mantissa gives `m = mant / 2^(52-k)`, and the result is `round_half_up(mant x 10^d / 2^(52-k)) / 10^d`, which is what `toFixed` does on the exact binary value (half-way cases included). `bad_mantissas` counts closes whose mantissa is outside [2^52, 2^53) (a zero or absurd mid); it must be 0.

Each judged bar gets its own recursion over its 600 closes (the shipped SQL does not use one long recursion over the whole history; both were shown to give identical bits, section 7). Mails: `public.signal_alerts` with `kind = 'signal'`, `interval = '1h'`, the exact rule id, `bar_time` (= the bar's OPEN) in the range, grouped per (pair, side, bar). Subscriptions are only counted (`signal_alert_subscriptions`, interval 1h, rule macdx; no `user_id`).

Performance notes for whoever edits `src/`: do not join the series inside the recursion (the planner chose nested loops and a 35 s run); keep the decimals `d` in `syms`; keep `fin` `materialized`; look closes up by rank in the per-symbol array (`closes`).

## 8. Limits and blind spots (what was NOT checked or cannot be seen)

1. **The three mails of 2026-10-13 have not been recounted by this toolkit, and the task's expectation "exactly three fires since go-live" cannot be shown today.** Key 20261013 is stored only after the GMO day ends (2026-10-13 21:00 UTC) and the sweep has read it, which the inventory saw at 00:00:03 to 00:00:07 UTC of the next day (one observation); so only the 10-12 mail (USD/JPY SELL 20:00) is a full `ok`. There are FOUR real mails of the rule (my own count query at 2026-10-13 10:59 UTC returned exactly these four groups, 1 row each, all `sent`, none for gold; the verifiers found the fourth at 09:01 to 09:34; `BRIEF.md` still lists three): USD/JPY SELL 2026-10-12 20:00 (1 row, `sent`, lag 3.117 s, entry 158.612), EUR/USD BUY 2026-10-13 01:00 (5.265 s, 1.11711), AUD/USD BUY 10-13 03:00 (3.962 s, 0.69607), EUR/JPY BUY 10-13 07:00 (4.722 s, 177.02). The first real test is the Routine run of **2026-10-14 00:16 UTC**. The inventory (`inv/pairs-spec.md` 4.5, **not verified by me**) expects macd -0.001013 / level 0.000433 for EUR/USD 01:00 and macd -0.000447 / level 0.000329 for AUD/USD 03:00. What to expect: for each pair `files_bid = files_ask = 1`; those three mails come out `ok` if the recount fires there; an `extra` or an unexpected `missing` is to be read with `near_edge` and `entry_diff_ticks` first. If the answer is `NO_DATA` again, the report must say "not checked". I tried to read GMO's live file from inside a SELECT (the database `http` extension, as the inventory did); the environment refused it in round 1 and I did not retry; whether the lead wants one read-only `http_get` SELECT for the 10 GMO files of 10-13 is for the lead to decide.
2. **Saturday-morning run:** according to the inventory (`inv/pairs-spec.md` 2.3 and 3.e; I did not re-measure it) the Friday day file is not in the table at 00:16 UTC (GMO builds that file when the new week opens, Sunday 22:00 UTC). The pairs answer will then be `NO_DATA` for all five (the Saturday-key and key-20261013 tests show what `NO_DATA` looks like). The Routine's Tuesday run counts the previous Friday key as well (the pairs statement a second time, with X minus 4 days); `mkday.py pairs KEY` works any time the file is stored. Gold on a Saturday: the sweep stops at Friday 21:00 UTC, so the stored row ends with the Friday 19:00 bar, and the 20:00 bar (it closes in the weekend window and is never judged) is absent; the answer is `CHECK` with `last_day_bar_not_at_day_end` after a full recount, because that attention test compares the day's last bar with `END_MS` minus one hour, not with the last judgeable bar (review finding F1, 2026-10-13). **Fixed in v4 only** (section v4.5: the v4 gold statement compares with the last judgeable bar; the v3 text is frozen and keeps this behaviour). Not run on a real Saturday yet (the v4 fix was tested on a stored row cut like a Saturday-morning read, section v4.7).
3. The Tuesday to Friday runs need the previous GMO day's file in the table by 00:16 UTC. The inventory saw this once (key 20261012 stored 00:00:04 to 00:00:07 UTC on 10-13: "one observation"); it is not guaranteed. If it fails, the answer is `NO_DATA` with the missing keys in `guard.missing_files`.
4. **Revisions:** pairs are recounted on the final stored files, production judged the live file 2 to 6 s after the close; gold is the LATEST row, production judged each bar on the row as it was about one minute after the close (bars may have been revised; per `BRIEF.md` the nearest known flip is a 0.78 USD change of the last close; the verifier found 0 revised cells among 1037 bars between the 06:01 and 09:01 reads). `near_edge` and `entry_diff_ticks` flag the cases; the 2-tick tolerance is not measured for 1-hour bars, and the size of real last-bar revisions on 1-hour bars is not measured.
5. **Subscriptions are only the count now.** Past subscription history is invisible: a recipient who has since unsubscribed makes a `dup` look like a duplicate, one who subscribed later is not missed.
6. Only `status`, `sent_at`, `closed_at`, `entry`, `side`, `bar_time` of `signal_alerts` are read; `skip_reason` and `error` are not. `sent_at - closed_at` is the mail service's acceptance time, not the inbox arrival.
7. **Winter time (US daylight time ends 2026-11-01) is untested.** The GMO day roll (21:00 UTC), the closure hours (Friday 22:00, Sunday 21:00 UTC) and the `weekend_window` hours are the summer constants; `rows_outside_key_day`, `closure_dropped` and bar counts would show a moved roll, nothing more. A reviewer (2026-10-13, finding F8, not verified yet) reads production's closure and weekend formulas (`isMarketClosed`, `isPossiblyClosed`) as the same in every season; if so, only the GMO day roll moves in winter and the closure and `weekend_window` constants must not be changed (task #358, before the run of 2026-11-03). A real holiday (fewer than 24 bars) was not tested; it would show as `last_day_bar_not_at_day_end` or `day_hours_missing`, i.e. `CHECK`.
8. Late revisions or purges of already stored day files, and the sweep's own errors, are not visible. The deployed bytes of `signal-alerts` were not compared with the reference tree (origin/main 30f662c); the verifiers only matched the version strings v26 / v27 in the sweep log.
9. The rule id (v3 `macdx_12_26_9_w600_1h_k0.8mv_v3`, v4 `macdx_12_26_9_w600_1h_z90of120_v4`) is written in the statements (mails, other-rule guard, RUN row); a new rule version needs the constants of section 10.
10. Not measured: win rate, profit or loss per trade, drawdown (the owner's rule: any win rate must come with the profit and loss per trade; this check has neither).
11. Run time: one day takes 0.6 s (pairs) / 0.15 s (gold); 4 days 0.9 s; the longest run was 139 days, 19.9 s. The database `statement_timeout` was not probed.
12. `test/x/*.raw` and `test/r2/ref/*` are a snapshot of 2026-10-13; the database files for past keys are not expected to change, the gold row does (the gold tests compare the bars up to 2026-10-13 08:00 with the 09:01 snapshot).
13. A subscriber who is not allowed (lapsed plan and not on the admin allowlist) gets no row at all, so every expected fire would show as `missing` although production did what it is built to do (section 4). The SQL cannot tell; the sweep's JSON answer (`not_allowed`) can, for the last six hours only.
14. A mail that production sent but whose row never reached the final `sent` status (a crash between the send and the update) shows as `not_sent` with `mail_status` `pending`; whether the person got the mail is not visible.
15. The equality branch `macd == level` (fires on equality) was hit by no real or made-up window; the SQL uses `g >= 0` with `g = macd - level` (SELL) or `-macd - level` (BUY), the same relation as the TypeScript `m >= level` / `m <= -level` by IEEE subtraction (by reading only). The branch "h == 0 keeps the previous side" WAS exercised by the verifier (5 windows, SQL = production = Python).
16. The independent Python recount belongs to the verifiers; it was written after reading the TypeScript, so it is independent in structure but not a clean-room rewrite.
17. The round-1 raw-tick replays (`e2e*`, `hist.sql`) were not re-run and were removed; they are replaced by the window-by-window comparison against the verifiers' production outputs (7,574 windows) and the rounding comparison of all 10,569 bars. The "+-1 tick" sensitivity of a decision is by formula (section 5), not by experiment.
